# S1 progress (ESA backend behind ISuffixTree, managed, no native code)

Rules: [PROCESS.md](PROCESS.md). Gates: [PLAN.md](PLAN.md) section S1 plus **peak RSS during build <= 24 B/char** (about 240 MB at 10 Mbp; Ukkonen peaks at 1.76 GB).
Pre-registered S1a gate (10 Mbp random DNA, 1 thread, this machine class): SA+LCP build <= 3.3 s (<= 10x libsais 0.328 s), index <= 16 B/char incl. text.
Targets: ceiling goal <= 1.0 s (3x), aspiration <= 0.5 s (1.5x); libsais reference 0.328 s, libdivsufsort 0.662 s, Go 0.73 s.

Decisions already taken by the owner: managed only; positions are `long` in the new contract from the start; contract-first (stable contract, replaceable engines);
Ukkonen stays untouched (oracle, online); ESA persistent container is a separate format kind; native accelerator not allowed.

**Owner requirement 2026-11-04 (categorical, supersedes ADR-003 / ADR-002 wherever they say "build in RAM, then write the file"):** the persistent index (SESA) must be built by **streaming straight into the memory-mapped files**; "build in RAM, then write" is rejected. Only a small fixed buffer is allowed; working memory must not grow with n. The input text may be read through a read-only mapping (it is the input, not the index). The in-memory backend is unaffected (its index lives in RAM by definition). Consequence: an external-memory / streaming construction algorithm must be chosen first; the S1a in-RAM kernels stay as the in-memory builder and as candidate building blocks, but are not the persistent builder. Selection: [ADR-004](adr/ADR-004-external-memory-construction.md) (research step, 2026-11-04; E0-E3 measured 2026-11-09 and B-DCS decided by the owner the same day, ADR-004 sections 5a and 6b): primary "B-DCS" = Karkkainen blockwise suffix sorting with a difference-cover sample in lexicographic buckets, LCP by a chunked external Phi/PLCP pass, child table by one scan with a spilling stack, navigation pack with Psi instead of ISA; fallback SAscan/pSAscan; prototype gates E0-E9 decide, owner questions Q1-Q9 open. S1b work packages 1b.7 (container writer) and anything that assumes an in-RAM build of the persistent file wait for ADR-004.

Answers to the S1-0 open questions (orchestrator, 2026-11-03; reversible, none touches a published format):
1. The 16 B/char gate applies to **Full** (index with the navigation pack); Core and Full are both reported.
2. The 3.3 s gate applies twice: S1a = SA+LCP <= 3.3 s; S1b = whole pipeline (SA+LCP+child table+navigation pack) <= 3.3 s.
3. Kind/extension name `SESA` / `.sesa` accepted as provisional (nothing is published yet, rename is free until the first release).
4. `NativeMemory` (BCL API, not P/Invoke, no native binary) is allowed from S1 on where it helps (large aligned arrays, no GC zeroing), always wrapped in an owning `IDisposable`/`SafeHandle`.

Design (S1-0, 2026-11-03): [ADR-001 index contract + suffix-link answer](adr/ADR-001-index-contract.md), [ADR-002 SA-IS, LCP, memory, optimization roadmap, JIT/AOT](adr/ADR-002-sa-construction.md), [ADR-003 SESA container](adr/ADR-003-esa-container-format.md).
Summary of the recommendations they contain: SA has n+1 entries (virtual `$`, `SA[0]=n`) so the ESA is node-for-node the Ukkonen terminated tree; the generic algorithms need only one navigator (suffix link called at exactly one place, `SuffixTreeAlgorithms.cs:477`, internal nodes only) and `Traverse`; suffix links are computed lazily as `LCA(Psi(lb), Psi(rb))` from an optional navigation pack (ISA + RMQ/PSV/NSV), not stored; SA-IS int32 with int64-ready generics; LCP by Phi/PLCP into a compact U8+overflow array; container kind SESA (magic `89 53 45 53 41 0D 0A 1A`).

## Test strategy (all work packages)

Oracle hierarchy (a mismatch at any level stops everything, PROCESS.md rule 3): L0 definitions and brute force (n <= 2000; exhaustive small alphabets); L1 the existing `...ByDefinition` implementations; L2 the in-memory Ukkonen tree; L3 the persistent v6 tree; L4 libsais output hashes (outside the repo); L5 `SuffixTreeSerializer.CalculateLogicalHash` and the `Traverse` event stream (equal across backends if H-OCC holds).

Differential on **every public operation** against L2 (and L3 for a subset): all members of `ISuffixTreeSearch`, `ISuffixTreeAnalysis`, `ISuffixTreeDiagnostics`, `ISuffixTree` (`ISuffixTreeSearch.cs`, `ISuffixTreeAnalysis.cs`, `ISuffixTreeDiagnostics.cs`, `ISuffixTree.cs:44-80`) with positive, absent, empty, single-character, longer-than-text and boundary patterns/queries; MEM/MUM/LCS/anchors with random and mutated queries (substitutions, indels, repeats), minLength 1..n. **Results the contract leaves implementation-specific are compared by property, not equality** (ADR-001 section 7): LRS representative on ties, `PositionInText` of `LongestCommonSubstringInfo` and of anchors (must be a valid occurrence; the match must be maximal), order of `FindAllOccurrences`.

Adversarial strings (deterministic and identical in the C# tests and the outside generator; PRNG = SplitMix64 with the seed in the name, because `System.Random` sequences are not stable across versions): `a^n`; runs (alternating letters, run lengths from the PRNG in 1..L, L in {2, 16, 256, 65536}); periodic with period p in {2, 3, 5, 7, 64, 65}; Fibonacci word (`f1 = "a"`, `f2 = "ab"`, `f(k) = f(k-1) f(k-2)`, truncated to n); Thue-Morse (`t[i] = popcount(i) mod 2`); de Bruijn sequences B(2,k), B(4,k) (FKM Lyndon-word construction, truncated or full); `a^k b a^k b ...`; random binary; random DNA (ACGT); random protein (20 letters); skewed alphabets (one rare symbol); all-distinct symbols (sigma = n up to 65,536); UTF-16: BMP characters above 255, valid surrogate pairs, lone surrogates, U+0000, U+FFFF; n = 0, 1, 2, 3; texts that maximise LMS count (`abab...`) and recursion depth.

Exhaustive small: all strings over sigma 2 up to length 14, sigma 3 up to 9, sigma 4 up to 7 (SA, LCP, tree statistics, `Traverse` stream, count of every substring).

Differential fuzz harness (built in 1a.7, extended in 1b.8): seeded generator families x alphabets x sizes, time/iteration budget from the command line, every failure prints `family seed n op` and is minimized (shrink by deleting/merging characters while the mismatch persists) into a regression file that becomes a permanent test; the harness is the same code that the S8 CI job will run.

Machine rule: tests may run only when no other build or test is running (`uptime`, `ps`, PROCESS.md:35); heavy categories (`Vectors`, `Performance`, long fuzz) are run explicitly.

- **Deviations from the ADR sketch and choices made** (ADR text not edited; the orchestrator decides): (1) **(b) is not a parent climb.** The child table of 1b.1 stores, for an interval, its first l-index at `rb` or `lb`, but no parent link, and neither the parent's bounds nor a way to reach them follows from a child's bounds without an outward search, so a climb from leaf `a` is not O(1) per step on this layout; (b) is the child-table descent along the rank path of `Psi(l)` from the root until the node of value `depth-1` (the walk of `EsaIndex.Search` without text comparisons; cost = children walked on the path to the target, about 3 table reads per level). A true climb needs the pyramid ((c)). (2) **(c2) added** as a fourth kernel (see above). (3) **R-SL point 2 of the ADR is not confirmed:** "use (a) in the first working version (WP 1b.4) because it is the simplest and is the oracle for (c)" would put an unbounded kernel (Fibonacci, Thue-Morse, periodic and `a^k b` texts) into the product; (c2) is as simple (two helper calls) and bounded, (a) stays what it is here, the oracle. The ADR line is for the orchestrator to amend; I did not touch the ADR. (4) The pyramid is not a sparse table over blocks: RMQ costs O(F x levels) sequential reads, 0.267 B/char at F = 16 (0.57 / 0.13 / 0.06 at F = 8 / 32 / 64; the ADR estimate "0.3-0.5 B/char, UNVERIFIED" is verified in order of magnitude); measured speed does not depend on F in 8-64, so 1b.4 can take F = 32 (0.13 B/char, (c2) steps max 123 on `rep_10m`). (5) The kernels read the LCP through `CompactLcp`'s indexer (a range check and a kind switch per read), not through pointers: the scan loops pay more for it than the pyramid does, all numbers are therefore a safe-code upper bound; the pointer kernels of 1b.4 will be somewhat faster, probably most for (a), which does not change the boundedness result. (6) The 1 locus driver is not the generic algorithm: `FindMaximalExactMatches` walks `GetChildren` / `CollectLeaves` from the minLength locus down to the longest-match locus; the driver replaces that by the outward LCP scan (same output, same left-maximality rule), so P2 measures the cost of matching statistics + links + rescans + emission, and the walk of the generic algorithm is the one cost it does not contain (on random DNA at minLength 20 the minLength locus is already inside a leaf edge, so it is nearly empty there; on `rep_10m` it is not, so the `rep_10m` figures are the less certain ones). (7) Process headers say `71c5dabaf3-dirty`: the data was measured with `71c5daba` plus the two-line fix of `cd6f63d2` (links not computed are skipped by the cross-check; a first set of runs showed exit code 3 only in the processes where the budget-limited descent was the comparison reference, the timing rows are not affected; that set was discarded and everything re-run).
- **Not verified / limits:** machines with a small L3 (only `dna_50m` leaves the L3 here); more than one thread (the structures are read-only, nothing concurrent was run); alphabets above 256 symbols in the driver (`NotSupportedException`, the kernels are alphabet-free); texts above 2^30 symbols (tagged child table); the end-to-end time of the real navigator through `SuffixTreeAlgorithms.FindMaximalExactMatches` (1b.4); MUM and anchors (proportional to the number of links, not measured); the cost of the `Pos = SA[Lb]` read that completes the target handle is inside the driver numbers (one SA read per link) but not in the P1 ns.
