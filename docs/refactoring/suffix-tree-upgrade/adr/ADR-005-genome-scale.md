## 0. The recommendation in one page, and the decisions that are the owner's

**What the measurements say (sections 2-4).**

1. **Stored width.** Four bytes (unsigned 32-bit, `POS_WIDTH` 4) is the fastest and the smallest, it already covers **n + 1 <= 2^32 - 1 = 4.29 Gbp, so the human genome (3.1 Gbp) needs no wider entry**; the builder of S1 writes 4-byte entries everywhere
   (`SesaBuilder.cs:546`, `Dist.cs:256-268`) and has no 40-bit path (ADR-004 section 4.3 planned one; it was not built). **Five bytes (40-bit) costs +2 to +31 % per random read and +6 to +13 % per count descent (four threads)**, but is **within 6-8 % of eight bytes on count and equal on locate** and 37 % smaller:
   it is the width for n above 2^32 - 4. **The hybrid with escapes is rejected**: at 6.2x10^9 it is *bigger* than 40-bit (5.79 against 5.00 B per entry), 1.26-1.28x slower on count and 2.9-3.6x on locate. A 34-bit line-packed form is rejected (15 % smaller than 40-bit, 1.16-1.25x slower on count, 2.2-3.2x on locate).
2. **The delta form for CHILD is the real lever** (the owner's own candidate of 2026-11-19, "a delta-from-index form with escapes for CHILD only"): on random DNA, a genome-like text and a repeat text **99.2-99.5 % of the child cells lie within 127 of their own index and
   99.99 % within 8,191**; stored as a 2-byte cell (kind in two bits, a 14-bit signed distance, the 0.006-0.01 % escapes in a hash table) the descent is **0 to 6 % slower than the 4-byte tagged cell at 10^8 (1.007 / 1.016 / 1.007 in the first session, 1.045 / 1.029 / 1.056 in the repeat on the pushed head; null experiments 0.97-1.02); at 5x10^8 it is 1.07 / 1.08 / 1.06 of the tagged cell and 0.99 / 1.02 / 1.00 of the packed 4-byte cell, which is the only 4-byte cell above 2^30 symbols**
   and CHILD is **2 B/char instead of 4 (Core 9.25 -> 7.25, Full 13.25 -> 11.25) independent of n**. The 1-byte form (1.0 B/char) costs +11-13 %. PSI increments are <= 255 in 99.92-100.000 % of the entries (1 B instead of 4: not measured for access cost).
3. **`long` instead of `int` in the hot loops costs nothing the instrument can resolve** (the count descent with `long` ranks and positions over the same 4-byte entries: the `int` code of `MappedSearch.Run` takes 1.01-1.05 of its time at four threads, i.e. `long` is not slower; the null experiment spans 0.95-1.03).
4. **The 2-bit text** is already the container's TEXT codec 4 (b = 2 for four letters, b = 3 for five to eight). Its read costs +34 / +45 % per random symbol (b = 2 / 3) against a byte (+1.0 / +1.3 ns), +8 % per dependent read, and **-13 % per long common extension** (26.7 against 30.8 ns for the 256-bit byte compare, 47.2 ns for the 8-byte compare).
   What S2 adds for DNA is the in-memory 2-bit text without a managed string and, as a stopping-rule experiment, a sigma = 4 kernel (section 4).
5. **The gate rows on this machine are close to met by S1 already** (100 Mbp: container in 17.6 s, 13.25 B/char Full / 9.25 Core; 5x10^8: **79.0 s Core, 104.7 s Full**, and **the libsais suffix array of the 5x10^8 text has the same SHA-256 as SA[1..n] of the container**, `6edf12d4...`: the checksum method of the gate works), with **one finding: the production chain's RssAnon is 342.1 MB (Core) and 344.6 MB (Full) at 5x10^8 (251 MB at 10^8), above the 320 MB gate of owner decision 2026-11-18** (section 11, risk R3).
   What S2 must still deliver is not speed but reach: a reader and an API above 2^31 (today a container above 2,147,483,646 symbols cannot be opened by any public call), the ingest, the public builder, the persisted navigation pack, `Structure` at scale and the hand-off.

## 2. The width of stored positions (item a): measurement

### 2.1 The question and the options

The owner's question of 2026-11-19: 4, 5 (40-bit) or 8 bytes per stored position, and whether a hybrid helps (short entries first, long ones after, as the Ukkonen v6 tree does with its compact zone and its jump table: `HybridLayout.cs`; a v6 node reference is an *offset*, allocated in order, so the first zone's references are small by construction; a suffix-array
entry is a *random* position, so a zone by rank does not work and a hybrid must be a hybrid **by value**, with an escape). Options measured, each on arrays of n entries whose values are uniform in [0, V) with V = 6.2x10^9 (both strands of the human genome: 30.7 % of the values do not fit 32 bits):

| option | layout | read |
|---|---|---|
| `w4` | 32-bit unsigned entries (SESA `POS_WIDTH` 4; the builder's) | one load |
| `w5` | 40-bit entries, byte-packed (`POS_WIDTH` 5) | one unaligned 8-byte load and a mask; 6.25 % of the entries straddle a 64-byte line |
| `w8` | 64-bit entries | one load |
| `hyb` | 32-bit slots, `0xFFFFFFFF` = long; per 64 slots a 16-byte record (escape bitmap, cumulative count); the long values at 40 bits; 4.25 B + 5 B x (share of long values) per entry | slot; on an escape: record, popcount, long array (two more dependent reads) |
| `p34` (an addition: the owner did not ask) | 34 bits per entry, 15 per 64-byte line (510 of 512 bits) | one line, a division by 15, a shift, a mask |
| `d16`, `d8` (the owner's CHILD candidate, 2.4) | the value as a signed distance from the cell's own index in 16 / 8 bits, escapes to a hash table | one load, a sign extension, an add |

### 2.2 Method (what is and is not resolved)

`analysis/s2/widthbench` (managed, anonymous memory from `NativeMemory`, 4 KiB pages like a mapped file: the transparent huge pages are `madvise` and .NET does not call it). **Synthetic rows**: `chase` (a chain of dependent random reads, restarted every 1,024 steps: the first version followed a random function into its cycle of about sqrt(n) entries, which stays in the cache; those rows were removed and re-measured),
`thr` (independent random reads: memory-level parallelism), `scan` (1,500 consecutive entries from a random start: the locate of an SA slice), `null` (the same loops on 4,096 entries: the decode and loop floor), at n = 10^7, 10^8, 5x10^8, 10^9 entries (the largest is 8 GB at `w8`: the 15 GB limit), 1 and 4 threads, 5-7 repetitions, median [min-max].
**Descent rows**: a copy of `MappedSearch.Run` over the **real container** (text and LCP in place, the suffix array and the child table re-encoded into the layout under test in anonymous memory), Trusted, 200,000 20-mers present in the text, 200,000 absent, and 10,000 8-mers for locate; the **variants are interleaved** (the order rotates each repetition) and the first two passes are warm-up; every variant must give the same
checksum over 100,000 patterns, and the first is checked against the product reader on 3,000 patterns (equal); `v1b` is a second copy of `v1`: **the null experiment of the instrument**. **What the instrument resolves**: the four-thread descent rows repeat within 1-3 % (`v1` against `v1b`: 0.985-1.026 over three sessions); a single-thread row has 25-40 % between its minimum and maximum (steal time of the VM) and is reported but not used to decide.
Drift control: the libsais `dna_10m` build at the start and the end of every session read 0.297-0.360 s against the S1 reference 0.328 s (ratios 0.90-1.10, "ok"; `results/drift_s2.tsv`).

It matters because **the builder must use the packed codec above 2^30 symbols** (`TaggedChild.MaxLength`, F8): at genome scale the 4-byte baseline is `v2`, not `v1`.
* **The delta cell**: see 2.5.

### 2.5 The delta form of CHILD (the owner's candidate) and of PSI

How far is a child cell from its own index? (`widthbench stats`, `results/child_stats.txt`; a cell holds the first l-index of a child interval or the next l-index of an interval.)

| text | n | cells within 127 of the index | within 32,767 | farther | empty cells | LCP escapes (U8) |
|---|---|---|---|---|---|---|
| random DNA | 10^8 | 99.54 % | 100.00 % | 0.00 % | 1 | 0 |
| genome-like (ACGNT, repeats, N runs) | 10^8 | 99.19 % | 100.00 % | 0.00 % | 1 | 1.39 % |
| repeat text (100 kbp block x 100, 1 % substitutions) | 10^7 | 99.22 % | 100.00 % | 0.00 % | 1 | (U16) |

For the 2-byte cell (14-bit distance, |d| <= 8,191) the escapes are **7,172 in 10^8 cells on random DNA (0.007 %), 7,444 on the genome-like text, 28,677 in 5x10^8**: they are the cells of the top of the tree, which every query touches, so **the lookup must be a hash table, not a binary search** (the binary search of `v8` costs +26 to +46 %; the hash makes it cost 0 to 6 % at 10^8).
* **`d16` (2 B/cell, kind in two bits, no LCP read, `CHILD` codec 3)**: 1.007 / 1.016 / 1.007 of the 4-byte tagged cell at 10^8 (the repeat on the pushed head, `results/verify_clone_dna_100m.tsv`: 1.045 / 1.029 / 1.056, against 1.016 / 1.057 / 1.026 for the packed cell and 1.065 / 1.077 / 1.227 for `w5` in the same run); at 5x10^8 it is 1.067 / 1.083 / 1.056 of it **and 0.99 / 1.02 / 1.00 of the packed 4-byte cell (`v2`)** that is the only 4-byte codec above 2^30. In bytes: **CHILD 4 -> 2 B/char for every n (the escapes grow like n/14,000 to n/17,000: about 3-4 MB of hash table at 3x10^9, extrapolated)**, Core 9.25 -> 7.25, Full 13.25 -> 11.25; independent of the position width, which removes CHILD from the width question above 2^32.
* **`d8` (1 B/cell, the kind told by LCP comparison, 0.46-0.81 % escapes)**: +11 to +13 % at 10^8, +22 % at 5x10^8 (the escape table is 2.4 million entries). CHILD 1.04 B/char (Core 6.3). Not recommended: it costs what `d16` does not.
* **PSI**: its increments inside a first-symbol bucket are <= 255 in **100.000 % (random DNA), 99.997 % (genome-like), 99.92 % (repeat text)** of the entries (the other entries are the 3-4 bucket starts and a few large steps): a blocked delta form (a 4-byte checkpoint every 64 entries, one byte per entry) would be about 1.1 B/char instead of 4. **The access cost was not measured** (a read is a checkpoint plus a prefix sum of up to 63 bytes: one or two cache lines and about 10-20 ns, UNVERIFIED); it is the S3 / S7 question (S7 replaces PSI by the BWT).

Measured anchors: a container of 10^8 random DNA symbols is 1,325,019,393 bytes = **13.250 B/char** with PSI (text 0.25, SA 4, LCP 1, CHILD 4, PSI 4), genome-like 13.486, repeat text 14.250 (`analysis/s1b-handoff/reference_hashes.tsv`); 5x10^8 Core (no PSI): 4,625,016,065 bytes = **9.250 B/char**. ### 2.7 What 6.2x10^9 would add, and what cannot be measured here

Arrays of 25-50 GB (5 B x 6.2x10^9 = 31 GB per section) are above this machine's RAM and disk: **not measured**. What the 10^9-entry rows already contain: the DRAM latency (165-245 ns) and the page walk. What 6.2x10^9 adds, **UNVERIFIED**: (1) the page-table entries of a 31 GB array are 62 MB, of three arrays 190 MB; this VM reports 480 MB of L3, so the walks still hit the cache here and the cost of a wider array is **under-measured relative to a machine with a 32-96 MB last-level cache** (the owner's Mac);
(2) arrays larger than the page cache turn every random read into a disk read: the E7 / 1b.9d result (1.73x slower at an effective cache of 0.71 of text + rank, 5.05x at 0.50) is the order of magnitude, for the builder; for the queries the page cache must hold the hot part (the top of the tree and the touched SA lines); (3) the hybrid's escape share is fixed by V (30.7 %), so its ratio does not improve with n;
(4) NUMA and transparent huge pages differ by machine. None of these changes the order `w4 < w5 ~ w8` of the count descent or the decision against the hybrid.

### 2.8 Decision, risk, what is the owner's

**Recommendation (O1):** `POS_WIDTH` 4 up to n + 1 <= 2^32 - 1; **5 above**, chosen once from n at PH0 (no promotion in mid-build); 8 defined and refused; no hybrid, no `p34`. **O2:** the builder stays at 2^32 - 4 (F7); the 5-byte reader and format are ready and tested by re-encoding. **O3:** CHILD codec 3 (`d16`).
**Risks:** (a) the descent cost of `w5` is +6-13 % and appears only above 2^32 - 4, which nothing in S2 builds; (b) `d16` is +7 % over tagged and 0 over packed at 5x10^8 (the kill rule of S2.13 is stated against the packed codec for n > 2^30, which is the real comparison); (c) the instrument cannot resolve 3 % on one thread: the decisions use four-thread rows and ratios of interleaved variants; the S2.3-S2.5 gates use `abapp`, whose noise floor is 1-2 %.

### 3.2 The additive `long` surface (exact signatures)

The `int` API stays as it is (the default of 2026-11-19, reversible). **What exists already**: `ISuffixIndex`, `ISuffixTreeNavigation`, `ISuffixArrayAccess` are `long` end to end and `EsaSuffixTree` implements them; what is missing is (a) a way to

### 3.3 The engine: `long` in registers, the stored width as a strategy

* **In-register type is `long`** for every rank, position, depth and count in the engine (`EsaIndex.*`, `LcpIntervalScan`, `LeftmostOccurrence`, `EsaNavigator`, `EsaNode` fields, `EsaStatistics`, the pyramid). Measured: the count descent with `long` costs no more than the code of today (the `int` code takes 1.01-1.05 of its time, section 2.4).
* **The stored width is a struct strategy** `IPosReader { ulong Get(long index); }` with `Pos32` (4-byte unsigned), `Pos40` (5-byte: one unaligned 8-byte load and a mask, 3 bytes of padding at the end of the section), `PosInt` (the in-memory `int[]`), and, for tests, `PosGen` (a function: 3.7).
  `SaView`, the child cells and the PSI / ISA views become `readonly struct XView<TPos>`; the **kernels are generic, the classes are not**: `MappedSearch.Run` is already specialised by access mode, LCP width and CHILD codec through struct type arguments (12 instantiations today); the position reader is one more argument (`Pos32`, `Pos40`: 24 instantiations, the JIT
  compiles only the ones a file needs). The choice is one `switch` per public operation, as `MappedSearch._variant` is today, not one branch per read. In-memory trees go through `PosInt` so that there is one engine.
* **Instantiation budget** (a risk, section 10 R2): positions {`PosInt`, `Pos32`, `Pos40`} x access {Checked, Trusted} x LCP width {8, 16, 32 (and 64 for n > 2^32)} x CHILD {packed, tagged, delta}; the matrix is listed in the code and every row is a test parameter; instantiations that cannot occur (`PosInt` with a mapped file) are not generated.
* **Overflow pairs of the LCP** (`LCP_OVERFLOW`, today `uint` pairs read as `int`) become `2 x POS_WIDTH` bytes (ADR-003 amendment 2026-11-19 already says `ELEM_WIDTH = 2 x POS_WIDTH`); the binary search runs over `long` ranks. LCP width 64 (`LCP` codec 4, defined in ADR-003) is needed only for a text above 2^32 with a repeat longer than 2^32 (`a^n`).
* **The navigation pack from the container** (F10, debt C of S1b): `PSI` (kind 12) is read in place; the suffix link is `LCA(Psi(lb), Psi(rb))` over the persisted `RMQ` pyramid (kind 9, optional, written by the builder: 0.13 B/char; the first suffix-link call builds it today with one pass over the LCP, cost not measured here, UNVERIFIED), so `Parent`, `SuffixLink`, `Lcp`, `Lca` need no heap. `ExtendLeft` and `RankOf` need ISA: for a container that has no `ISA` section and whose
  `n` is above `PackHeapLimit` (proposed 2^28 = 1 GB of ISA) they are `Unsupported` with a note (capability matrix of ADR-001 amended), not an out-of-memory error.

### 3.4 The effect on the hot loops, and how it is measured

The rule of the owner: **no loss against the S1 gate rows** (`analysis/bench/results_1b9_*`). Evidence so far, from the prototype copy of the descent (`analysis/s2/widthbench`): `long` ranks and positions over the same 4-byte entries take **0.96-0.99 of the time of the `int` code at four threads (the `int` code is 1.01-1.05 of the `long` code)** (count of present / absent 20-mers, 10^7, 10^8, 5x10^8; null experiment
`v1` against `v1b` 0.98-1.03). Measurement plan for the packages, in order of strength:
1. the in-process **A/B instrument `abapp`** (`analysis/bench/abapp`): the S1 head (`703d6036`, built to its own directory as `bin_s1`) against the S2 head on the same containers and pattern files, count and locate, 1 and 4 threads, ABBA blocks, null experiment first; threshold **0.97 of the S1 head** (the gate flags of 1b.9g.1), file-backed `Checked` and in-memory. **The null experiment is on record** (`scripts/run_abapp_null.sh`, `results/abapp_null.tsv`: the same build against itself on `dna_100m`, four threads, three processes of seven blocks): per process 0.968-1.058 on the three operations, **pooled median 0.995**; so a single process cannot resolve 3 %, and every gate pools at least five processes, as 1b.9g.1 did (22);
2. the S1 gate rows themselves (`run_1b9_gate.sh build|query|nav|open` on `dna_10m`, `dna_1m`, `rep_10m`, `prot_1m`, five fresh processes, libsais control at the start and the end) on the S2 head: 1.138 s build, 647,176 count/s, 990,228 locate/s, 10.00 B/char, RssAnon <= 286.3 MB (the numbers of `PLAN.md` status);
3. a regression of the *in-memory builder* is excluded by construction (it stays `int`; S2.3 does not touch `SaisKernel`/`LcpKernel`), and by a byte-identity test of the SA/LCP/CHILD arrays against the S1 build on `dna_10m`, `rep_10m`, `prot_1m`.

### 3.6 `Structure` and `Sections` above 2^31

`Header` is O(sections) and needs only `long` fields (already `long`). `Sections` (CRC-32C of every payload) is a sequential pass: chunked by 16 MiB views, needs no change beyond `long` section lengths (measured 4.8-5.3 GB/s with the instruction). **`Structure`** is the problem: the Phi pass reads the SA once per chunk of 4 Mi positions
(about n^2 / chunk: 24.7 s at 10^8, **about an hour at 3x10^9, UNVERIFIED** (debt C of S1b)). Options: (1) **reuse the chunked distribution of PH4** (`External/Lcp`: Phi/PLCP by `Dist`, I/O 33-45 B/char, scratch up to 12 B/char = 36 GB at 3x10^9) so that the check is linear: recommended (O12), about 6 h; (2) keep the quadratic pass and document "run by the owner, hours";
(3) a sampled structure check (random ranks) - a different guarantee, not recommended as a level. The level never needs more than the bitmap n/8 (0.4 GB at 3x10^9) and the chunk buffers of the existing pass.

### 3.7 Testing n > 2^31 on this machine (15 GB RAM, 16 GB disk, no P/Invoke)

Four layers, each said with what it proves and what it cannot:
1. **Generator-backed readers** (`PosGen : IPosReader`, plus generated LCP and child cells): periodic texts whose SA, LCP and child table have a closed form (`a^n`: `SA[r] = n - r`, `LCP[r] = r - 1`, a chain of nodes; `(ab)^m`; `a^k b a^k b ...`), so the **generic engine runs at n = 2^31 + 10, 2^32 + 10, 2^33, 2^40 with no memory at all**: every query (count, locate paging, `Traverse` statistics, navigation, LRS, `Lcp`, `Lca`) is compared with the closed form. *Proves*: no `int` overflow, sign extension or narrowing cast on the paths that run, the 40-bit decode of values above 2^32,
   the LCP of 64 bits. *Cannot prove*: anything about a mapped file, page faults, a text that is not periodic (the child table has only two children per node), speed.
2. **Sparse containers**: a SESA 1.1 file of 2^32 + k symbols created with `SetLength` (a sparse file costs no disk blocks: the volume is 252 GB nominal, 15-18 GB free) whose header and section table are valid and whose **zero sections are valid for `Sections`** (the header carries the CRC-32C of n zero bytes, computed by the CRC combine, not by a pass), plus the few non-zero pages that a chosen query touches (a^n again). *Proves*: the file and mapping arithmetic above 2^31 and 2^32 (offsets, `long` section lengths, `Span` creation from a pointer with an `int` length is the classic failure), the dispatcher, `Header` and `Sections` at 4-20 GB, the error for a hole read.
   *Cannot prove*: real data, durability, disk-full, the write path.
3. **Width-parametrised conformance**: every existing container test (those among the 3,900 default Esa tests that open a container) is run twice, over a 4-byte container and over its **re-encoding to `POS_WIDTH` 5** (a test-only tool `Sesa5Encoder`: the same content, 5-byte entries), at n <= 10^6: *proves* that the 40-bit reader is a reader of the same index (answers equal, `Structure` passes, the corruption fuzz catches the same damage).
4. **The owner's hand-off run** (section 8) at 3x10^9: real memory, real page cache, real time, `Structure` at scale. *Only this proves* the claim "works at >= 3 Gbp" (C13 level 3); layers 1-3 make a failure there unlikely and, if it happens, local.

A second periodic family is worth its cost if the first three are cheap: `u^m` for a **de Bruijn word** `u` of order 10 (4^10 = 1,048,576 symbols, fan-out 4 at every level down to depth 10, then the periodic tail; `m = 2^13` gives n = 2^33): its SA and LCP follow from the **cyclic suffix array of one period** (which the production builder makes in 1 s) by a closed rule (suffixes of the same rotation are ordered by length, those of different rotations by the cyclic order unless the shorter ends first), with the child table produced by the engine's own scan over the generated LCP (about 10^10 steps, minutes: a `Large` test). A de Bruijn word *itself* (all k-mers distinct, fan-out 4 at every level) has no closed-form suffix array: it can be built, up to 5x10^8 symbols, by the builder here, and above that only the owner's run reaches fan-out 4 at depth 15 and more with n > 2^31.

What none of them reaches: a text above 2^32 - 4 with real data (O2: the builder cannot write one; a 5-byte container of real data exists only by re-encoding, up to 4.29 Gbp, which this machine cannot hold either).

## 4. The 2-bit packed text and the sigma = 4 fast path (item c)

### 4.1 What exists

The container's `TEXT` codec 4 (ADR-003 amendment 2026-11-18) already stores `b = max(1, ceil(log2 sigma))` bits per symbol (2 bits for four letters, 3 for five to eight, 4 for nine to sixteen), big-endian bit stream, 64 zero bytes of padding, written by PH0 straight into the section through mapped windows (`External/PackedTextFormat.cs`, `PackedTextWriter.cs`), read by `MappedTextReader` (64-bit
windows, 256-bit compare) and by the descent (`MappedSearch.Symbol`, a 16-bit load and two shifts). **So the container side of "2-bit packed DNA text" is done**; the 9.25 B/char Core of section 2.6 already contains text at 0.25. What does not exist: (a) a packed text for the **in-memory** index (it holds the caller's `string` at 2 B/char plus a `PreparedText` of one byte per symbol;
`TextPreparation.Prepare` takes `ReadOnlySpan<char>` only), (b) a way to build an in-memory index from a text that never was a string (a managed string cannot exceed about 1.07x10^9 characters), (c) a kernel specialised for sigma = 4.

### 4.2 Layout decisions

| question | options | decision (default) |
|---|---|---|
| bits per symbol | b = ceil(log2 sigma) (today); 2 bits + exceptions | **b = ceil(log2 sigma)**. The exception list saves 0.125 B/char (1.3 % of Core 9.25) and costs a consultation of the list on every text read or a false match inside an N run; **no exception list** (O5) |
| non-ACGT | keep as letters (sigma 5-8, b = 3); refuse; remove with a gap map | **keep** (exact semantics, nothing hidden); *refuse* is an ingest option (`NPolicy.Reject`); *remove N runs and record a gap map* changes the meaning of positions and creates false junction matches: **an S4 decision** (PLAN S4: "policy for N in the indexed text"), not made here |
| case (soft masking) | keep as letters; fold to upper | ingest option `CaseFold` (default **fold**: the index is of the sequence, the mask is a separate annotation); folded runs are not recorded (a `CASEMASK` section is not proposed) |
| record separator in a multi-record text | a symbol outside the alphabet; none | **none** for a packed DNA text (a separator makes sigma 5: b = 3 for every genome); the record table `DOCMAP` (section 7.2) gives the boundaries; **a match may cross a boundary**, S3 filters by `DOCMAP`; byte and protein texts may carry a separator symbol as today |
| terminator | stored; virtual | **virtual** (`SA[0] = n`, `text[n] = -1`): unchanged |
| header | a `TEXT_KIND` field; none | **none**: the kind is told by the `ALPHABET` letters and the `TEXT` codec (a header hint would be a second source of truth). S4 reads the letters (A, C, G, T / U, N, IUPAC) to decide what N and IUPAC mean |
| protein and byte texts | - | **stay byte texts** (codec 1/2 or codec 4 with b = 5 for 20 letters, as today) |

### 4.3 The cost of reading it (micro-benchmark, `results/text_bench.tsv`; 10 Mbp, median of 9, spreads <= 1 %)

| operation (ns per operation) | byte | 2 bits | 3 bits | note |
|---|---|---|---|---|
| independent random symbol read (the induction and naming passes of SA-IS, the leaf compare) | 2.84 | 3.80 (x1.34) | 4.13 (x1.45) | one 16-bit load, a byte swap, two shifts |
| dependent random read (the latency of one descent step) | 12.46 | 13.40 (x1.08) | 13.52 (x1.08) | the cache miss dominates |
| sequential scan, per-symbol decode | 0.29 | 0.84 (x2.9) | 0.84 (x2.9) | a pass by words would be faster; the SA-IS kernel never scans the text sequentially except once, in the classification |
| common extension of two random positions (about 1.3 symbols, on `dna_10m`) | 6.7 (8-byte compare), 7.8 (256-bit) | 11.0 (x1.64) | 12.5 (x1.86) | the fixed cost of two unaligned 64-bit windows |
| common extension of two positions 100 kbp apart in `rep_10m` (about 50 symbols) | 47.2 (8-byte), 30.8 (256-bit) | **26.7 (x0.57 of 8-byte, x0.87 of 256-bit)** | 41.9 | 32 (21) symbols per 64-bit step against 8 |

Reading: a packed text is **slower per isolated symbol (+1.0 to +1.3 ns, +8 % on a dependent read) and faster per long compare (-13 % to -43 %)**, and it makes the text 4x (2.7x) smaller, which is what matters when the text no longer fits the cache (100 Mbp: 25 MB against 100 MB). In the count descent the text read is one of about four reads
per step, and the 4-thread descent of the container (which reads the text packed in every row) is the S1 row (1b.9a: 0.5 / 3.1 / -1.2 % against the in-memory tree). **UNVERIFIED**: the effect of b = 2 against b = 3 on the same descent (the micro-benchmark says +9 % per read; the descent has no separate row).

### 4.4 What changes in memory, and the sigma = 4 kernel

* **In memory**: a `PackedDnaText` (owning, `NativeMemory` or a mapped file; 2 or 3 bits; `ISymbolReader` and `IPtrText` over it; `n/4` bytes: 125 MB at 5x10^8) as the *text of the in-memory index* (no string, no `PreparedText` copy): the in-memory index is then SA 4 + LCP 1 + CHILD 4 + text 0.25 = **9.25 B/char** against 10.00 + the caller's 2 B/char string = 12.00 today, and a text that never was a string can be indexed (`EsaSuffixTreeFactory.Create(PackedDnaText)`).
* **The sigma = 4 fast path in SA-IS and LCP**: the S1a-opt iterations already pack symbol and S/L type in one byte (`PackedBytes`, 1o.1c: -22.6 %); the kernels read the text through `ISymbolReader`/`ITypedText` structs specialised by the JIT per width. A 2-bit input adds a reader (`Packed2Symbols`) and a nibble-packed typed form (symbol 2 bits + type 1 bit in 4 bits: half the cache footprint of the induction's random reads).
  **No gain is claimed**: the micro-benchmark above says a random read costs more, the saving is in cache misses (UNVERIFIED). It is an **experiment with the stopping rule of PROCESS.md** (S1a-opt style: accepted only if the SA + LCP build of `dna_10m` and `dna_100m` is >= 3 % faster in the median of five fresh processes against the S1 head, and byte-identical output; else reverted): package S2.9, second half.
* **Peak RSS of the in-memory build** (15.4 B/char today, gate 24) falls by the same 0.75 B/char.

## 5. Integer alphabet (item d)

* **The contract has `int` symbols** (`ISuffixIndex.TryExtendRight(locus, int symbol)`, ADR-001 rule 1: "UTF-16 code units 0..65535, -1 = terminator; integer alphabets are added in S2 as a second overload set").
* **What the in-memory index already supports**: the kernels are generic over `ISymbolReader`; `IntSymbols` and `SymbolWidth.Int` exist (the reduced strings of the SA-IS recursion are `int` symbols with an alphabet as large as n/2), the LCP kernel and the child scan do not depend on the alphabet. What is missing is plumbing: `TextPreparation.Prepare` takes `ReadOnlySpan<char>`, `PreparedText` has `byte` and `ushort` arrays, the pattern search maps `char`s through `Alphabet`.
* **What a container needs**: an `ALPHABET` with letters above 255 (`ELEM_WIDTH` 4; the reader refuses them today: `SesaHeaderReader.cs:144`), a `TEXT` codec for b > 8 bits, and above all **a builder over `int` symbols**: PH0-PH6 read bytes (`PackInto(ReadOnlySpan<byte>)`, the rank files, the key of 64/b symbols in `Sort/*`, `Dcs/SampleNamer.cs`): 25-40 h, UNVERIFIED.
* **Consumers** (PLAN section 8): R1 (protein, about 25 letters), S3 (documents: a separator symbol outside the alphabet), S4 (IUPAC): all fit a byte alphabet of at most 256 letters. No consumer needs more than 255 letters or a code unit above 255 in a container.
* **Cost and recommendation (O6)**: in memory about 4 h (`Prepare(ReadOnlySpan<int>)` with a dense remap by sort or radix over the distinct letters, `PreparedText` with an `int[]` and `int[] Alphabet`, the `ReadOnlySpan<int>` overloads of 3.2, tests with letters above 65,535, negative letters refused). **Yes for memory (S2.10, optional), no for the container**; the letter-width field is *defined* in 1.1 (section 6) so that nothing is redone.

## 6. Container format: SESA 1.1, the delta to ADR-003 (item e)

ADR-003 is not edited; this is the amendment text it would receive (the status line of ADR-003 names the amendments by date; this one is "2026-11-24 (ADR-005)").

**Name and negotiation (O7).** Every change is additive, so the format is **SESA 1.1** (`VERSION_MINOR` 1), the "v7" of PLAN.md. A reader of major 1 opens any minor and ignores unknown non-required sections; unknown required sections and unknown codecs of required sections are refused (ADR-003 section 7, unchanged). A 1.0 reader meeting a 1.1 file that uses `POS_WIDTH` 5 refuses it
(`SesaHeaderReader.cs:96-97`: width 8 is `NotSupportedException`, any other width but 4 is `InvalidDataException("POS_WIDTH is 5: 4 or 8")`: it fails closed, with a damage message that the S1 code cannot improve); a 1.1 reader opens every 1.0 file unchanged. The dispatcher `SuffixIndexFactory.Open` is unchanged for v6 (its magic) and for SESA (the magic); it learns nothing new except `OpenIndex` (3.2). **v6 and SESA 1.0 stay readable and writable as today**: the migration test is a set of golden files of both, committed once (the 12 reference containers of `analysis/s1b-handoff/reference_hashes.tsv` at 10^6 are the candidates), opened by every future reader.

| ADR-003 item | change |
|---|---|
| header `POS_WIDTH` (offset 72) | allowed values **4 and 5** (8 stays refused with the `NotSupportedException` of `SesaHeaderReader.cs:96`); 4 requires `n + 1 <= 2^32 - 1`, 5 requires `n < 2^40`. **The writer chooses it once from n at PH0**, so no promotion in mid-build exists. |
| `TEXT_LEN`, `NODE_COUNT`, `LRS_*`, `FILE_SIZE` | already 64-bit fields: no change; the reader accepts `TEXT_LEN` up to the limit of the width |
| sections `SA`, `CHILD`, `PSI`, `ISA`, `BUCKET` | `ELEM_WIDTH = POS_WIDTH` (5: entries byte-packed, little-endian, the last entry followed by 3 bytes of padding that belong to the payload so that the reader may load 8 bytes at any entry) |
| `LCP_OVERFLOW` | pair width `2 x POS_WIDTH` (10 bytes at 5); `LCP` codec 4 (U64) is used when the text has a repeat longer than 2^32 - 2 |
| `CHILD` | codec 1 (packed) and 2 (tagged, `n <= 2^30 - 1`) as they are; **codec 3 (new, optional per O3): the 2-byte delta cell** of section 2.5 (kind in bits 14-15, signed distance in bits 0-13, -8192 = "see the list"), `ELEM_WIDTH` 2, `COUNT` = n + 1, `REQUIRED`, `HAS_CRC`; the escapes in an optional section kind 15 `CHILD_ESC` (sorted pairs `(cell, value)`, `2 x POS_WIDTH` bytes; the reader builds a hash table at `Open`: 0.7 ms per 10^5 escapes, UNVERIFIED) |
| `RMQ` (kind 9) | defined by ADR-003 as "block minima + sparse table"; **redefined** as the persisted LCP pyramid of `EsaNavigationPack` (fanout 32, 0.13 B/char), `PARAM0` = fanout; written by the builder when the pack is asked for, so that `Open` does not rebuild it |
| `TEXT` codec 4, `ALPHABET` | unchanged (b <= 8, letters < 256); `ALPHABET` with `ELEM_WIDTH` 4 and a codec for b > 8 are **defined as reserved** (the integer alphabet of the container, O6) and refused |
| new optional kind 14 `DOCMAP` | record names (UTF-8) and start offsets (`POS_WIDTH` bytes), written by the FASTA ingest (section 7.2); `REQUIRED` clear |
| header reserved bytes 120-123 | stay 0 (no `TEXT_KIND`, section 4.2) |
| `Structure` | defined at any n (section 3.6); the per-level cost table of ADR-003 section 6 gains the row "O(n) I/O, scratch 12 B/char above 2^31" |

**Effect on the writer.** There is no class `SesaWriter`: the writer is `SesaFormat` (header page, section table: `SesaFormat.cs:57-59` has `VersionMajor = 1`, `VersionMinor = 0`, written at `:120-121`) and `SesaBuilder` (the sections). **There is no SESA 2**: the only format version that exists is 1.0.  The builder **already writes v1.1-shaped sections** in every respect except the version word: 4-byte sections with `ELEM_WIDTH = POS_WIDTH = 4`, TEXT codec 4, CHILD codec 1 / 2, PSI kind 12, COUNTS kind 13, `ALPHABET` ELEM_WIDTH 2. Changes: (1) `VERSION_MINOR = 1` only when a 1.1 feature is used (a 1.0-shaped container is still written as 1.0, so that all 12 reference hashes of the S1 hand-off stay valid byte for byte: **a test**);
(2) `RMQ` and `DOCMAP` writers; (3) CHILD codec 3 if O3; (4) `POS_WIDTH` 5 is **not written by the builder** (O2); it is written by the test-only re-encoder `Sesa5Encoder` (section 3.7) and by the future 40-bit builder.
**Verifier levels**: `Header` and `Sections` as in 3.6; `Structure` linear (O12) with `POS_WIDTH` 4 and 5; the check that a 1.0-shaped container carries minor 0 and a 1.1 one carries a feature that needs it. **Migration test plan**: golden v6 and SESA 1.0 files open in every build of the family; a 1.1 file with `POS_WIDTH` 5 is refused by a build of the 1.0 reader (kept as a test project reference to the S1 tag / a frozen copy of the 1.0 header reader); 4 -> 5 re-encoding round trip (every query equal); minor-1 without a feature is refused as damage.

## 7. Build from FASTA or a stream; the public builder (item f)

### 7.1 Today

`SesaBuilder.Build(input, target, options)` takes a **path of a text file of bytes** (one symbol per byte, no header, no line break), reads it **twice** through a read-only mapping (PH0: pass 1 counts the distinct symbols and the symbol counts, pass 2 packs b bits per symbol into the TEXT section through mapped windows), so the text never exists as a managed string and the working memory is the 1 MiB
blocks and the mapped windows. It cannot read FASTA, a record, a stream (a second pass is needed), a compressed file, and it is `internal`.

### 7.2 The ingest (the entry points, the memory bound)

* `IIndexInput` (new, public): `FromTextFile(path)` (today's behaviour), `FromFasta(path, FastaOptions)`, `FromStream(Stream, FastaOptions or TextOptions)`, `FromMemory(ReadOnlyMemory<byte>)`. `FastaOptions`: `CaseFold` (default true), `NPolicy` {`Keep` (default), `Reject`}, `Records` {`Concatenate` (default), `First`}, line endings LF and CRLF, `;` comments refused, a header line `>name` starts a record.
* **FASTA from a file**: PH0 runs its two passes through a streaming parser (1 MiB blocks): pass 1 validates, counts the letters after the policy and collects the record table (name, start, length); pass 2 packs. Cost: one more branch per byte (the parser is a table-driven state machine, a 256-entry map; **UNVERIFIED**: about 1-2 ns per byte against the 0.7-1.5 s per 10^8 of today's pass 1; PH0 is 2.7 % of a 5x10^8 build: 0.69 s of scan and 1.47 s of packing in 79.0 s).
  Memory bound: the blocks, the 256-entry map, the record table (a record costs its name plus 16 bytes: a genome of 25 records is nothing; a draft assembly of 10^6 contigs is about 60 MB, **bounded by writing the names straight to the `DOCMAP` section file**, so O(1) anonymous memory).
* **A stream** (a pipe, stdin, a `GZipStream`): it cannot be read twice, so it is **spooled once** into a clean byte file in the work directory (n bytes of disk, 3 GB for the human genome, 10-30 s) and then built as a text file. The spool is deleted at the end and is the reason a stream input names a work directory.
* **No managed string at any point**; for the in-memory index `PackedDnaText.FromFasta(path)` (n/4 bytes of native memory, one pass: the alphabet is known only at the end, so it packs at b = 3 and repacks to b = 2 if only four letters occurred, or counts first: the file is read twice anyway).
* **`DOCMAP`** (optional kind 14, O9): record names and start offsets, written by the ingest, read by S3 (`DocumentOf(position)`, document listing). No separator symbol (section 4.2).

### 7.3 The public builder question (R05 / re-score 1b.11: C14, C15, F03)

The builder is `internal`; the only routes are the Bench command and `s1b.sh`; the scale scores that "CLI-only when an API is expected" (F03 = 1, C14 3 -> 2, C15 2 -> 1; `analysis/review/1b11_rescore.md`). A public build entry raises C14, C15 and F03 together.

## 11. Debts of the S1 code that S2 touches (reported, not fixed)

1. **The RssAnon gate of the production builder at 5x10^8** (R3): 342.1 MB, verdict "Exceeded" in the Bench's own row; E7's prototype figure was <= 214.5 MB at 5x10^8. Not a defect of correctness; a gate of S1 that holds at 10^8 and not above.
2. **`SesaFile` with `n >= int.MaxValue` leaves `_lcp` and `_child` as `null!`** (`SesaFile.cs:62-63`) and `EsaIndex.FromFile` passes them on: any member access is a `NullReferenceException`; the facade's guard hides it (F4). Removed by S2.3.
3. **`EsaSuffixIndex` narrows every `long` argument with `(int)`** (F9) and relies on a constructor guard; one removed guard would wrap silently. Removed by S2.4.
4. **The dispatcher lives in the Esa project and drags `SuffixTree.Persistent`** (R03, `SuffixTree.Esa.csproj:12-14`): S8 (packaging); S2.7 adds version negotiation to this dispatcher and must not widen the dependency (an inversion by a registered loader is the S8 option).
5. **R06, R10, R02, R04** are in S2.6, S2.6, S2.12, S2.2.
6. **`SesaVerifier.RequireSupportedLength` and the README item 5** state a limit that S2 lifts: both are rewritten from `IndexLimits`.
7. **The `Structure` spill file** in the system temporary directory (`esa-verify-*.stack`, README item 20, R12 of the review): the S2.8 scratch option gives it a directory.
8. **`PackedTextFormat.MaxSymbols = uint.MaxValue - 3`** and the 12 files of 32-bit records are the builder's design limit (F7); a text above it is refused with a message that names it, in S2.12's options validation (not silently at the first `uint` overflow).
9. **The BWT pass of PH6 is superlinear**: 1.7 s at 10^8, 16.8 s at 5x10^8 (9.7x for 5x the data; the PSI pass 0.9 s -> 4.3 s is linear): the Full container costs +32 % of the Core build time at 5x10^8 against +15 % at 10^8; the 12.4-minute estimate for 3x10^9 (ADR-004 E6, prototype without PH6) must carry this factor (about +2 to +5 minutes, UNVERIFIED). Reported, not investigated.
10. **The first-`Open` JIT cost** (13-15 ms, 1b.9 A9) grows with the instantiations of R2: ReadyToRun in S8 is the remedy, measured again at S2.15.

## 14. Reproduction and protocol of this package

`analysis/s2/README.md` says how to reproduce every row; the protocol is that of `PROGRESS-S1.md` "Measurement protocol for the gate" with these differences, all stated where they matter: anonymous memory instead of a mapped file for the synthetic arrays (the same page size); the descent variants are interleaved inside one process (the S1 instrument `abapp` is the one for the gates of the packages, because it compares two builds of the product);
five to eleven repetitions per row with median and min-max; the libsais control at the start and the end of every session; machine load printed before every timing. **What was verified twice**: the 5x10^8 production build (79.0 s / 342.1 MB Core, then 104.7 s / 344.6 MB Full: the RssAnon figure reproduces), the `v1` against `v1b` null experiment in every descent session (0.95-1.03), the drift control (0.90-1.10 in 20 readings).
**Not measured here, said once**: any text above 5x10^8 symbols; arm64, macOS, Windows; a 5-byte container of real data (O2); the access cost of a delta-coded PSI; the FASTA parser (not written); the sigma = 4 kernel (not written); a cold page cache; the effect of b = 3 against b = 2 on the descent itself.
