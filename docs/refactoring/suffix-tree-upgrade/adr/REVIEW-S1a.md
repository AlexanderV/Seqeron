## 2. Methodology (what the numbers contain)

* `build_sa_s` = `TextPreparation.Prepare` + `SaisReference.Build`, `build_lcp_s` = `LcpReference.Build` (`apps/SuffixTree.Esa.Bench/Measure.cs`, `Pipeline.Build`; `Commands.cs`, `Build`). `Stopwatch.GetTimestamp()` brackets only these calls. **Included:** the dense remap (0.0385 s = 2.6 %, allocation of the 10 MB `byte[]`), every array allocation of the build (SA 40 MB, `bool[]` types, bucket arrays, Phi/PLCP 40 MB, compact LCP 10 MB; the allocator's zeroing and first-touch page faults), the cold JIT and tiering (generic instantiations `SaisReference<int>.Sais<ByteSymbols>` and `<IndexSymbols<int>>`, OSR) because each repeat is a fresh process, and the escape-counting pass and the compact-LCP construction (`LcpReferenceOfT.cs:32-52`, 1.2 % + 6.8 %). **Excluded:** reading the file and widening it to a UTF-16 `string` (`Pipeline.LoadText`), runtime start-up, the SHA-256 of SA and LCP and the vector comparison (after the timers and after the VmHWM read).
* **Fairness against libsais.** The libsais figure is `libsais()` + `libsais_plcp()` + `libsais_lcp()` with `clock_gettime(MONOTONIC)` around the three calls (`libsais_time2.c`); the text is read before the timer, SA/PLCP/LCP are `malloc`ed before it (pages first touched inside the timer, like fresh .NET arrays). Differences that cut each way: ours also remaps UTF-16 to bytes (+2.6 %) and pays the JIT (cold 1.38 s vs steady 1.286 s: ratio 2.49 cold, 2.32 steady), and counts escapes; libsais writes a full int32 LCP (4 B/char) where ours writes U8 (1 B/char) and so does less memory traffic in pass 3. Neither flatters materially. I also checked the reference is not handicapped: the library was built `-O3` without `-march=native`; a build with `-march=native` gave 0.567 s (n=5) vs 0.581 s (n=5), no difference; a build without OpenMP equals the OpenMP library; `fs` (free space after SA) 0 / 4096 / 10^6 / 10^7 gives SA 0.307-0.364 s each, no gain. The reference is the real libsais speed on this machine.
* **VmHWM** is per fresh process (`/proc/self/status` read right after the build), and it **includes** the 20 MB managed input string (2 B/char), the harness and the .NET runtime floor (VmHWM after load: 50.1 MB, about 30 MB without the string). It also counts transient garbage that the GC has not yet released. So it is conservative, not flattering; the 24 B/char gate of ADR-002 counts the string too. The wait4 value is the maximum over the whole process life (it also covers the hashing after the timers and the loader) and is about 7 MB higher.
* **What could flatter, and does not change the verdict:** (1) all four measured corpora are DNA/protein; the adversarial 10 Mbp texts measured by me (below) are faster than random DNA (`a^n` 0.38 s, `abab` 0.50 s, Fibonacci 0.81 s, Thue-Morse 0.92 s), but have a **4 B/char LCP** and a higher peak, see MAJ-3; (2) the 3.3 s gate is met by 2.3x on the cold number, but the ratio quoted for the stopping rule (2.5x) is cold vs AOT; (3) one machine class with a 480 MiB L3 (cache effects hidden, as ADR-002 R3 says); (4) `bench_esa.tsv` rows equal the Log (checked row by row: 1.409731 / 1.083073 / 0.312409 / 156164096 / 163749888); nothing in the table was transcribed wrongly.

## 3. Findings

### MAJ-1 Nothing detects out-of-bounds access after the move to pointer kernels
* **Claim.** ADR-002 R1 / PROGRESS 1o.1: `int*` kernels without `Span` indexers; the safety argument is "bit-identical SA vs `SaisReference`, fuzz, `DOTNET_JitDisasm` shows no range checks".
* **Evidence.** Mutants M04 (`isS[-1]`), M26 (`text[n]` read in the PLCP loop) and M38 (`map[1023]`) are killed **only because the safe code throws** `IndexOutOfRangeException` (of 51, 41 and 16 failing tests, 50, 38 and 15 report `System.IndexOutOfRangeException`; the output of M26 would be the right answer whenever the byte behind the text happens to differ). M25 shows the PLCP bound `j + l < n` is dead for a valid SA (the predecessor never has suffix j as a proper prefix) yet is the only guard when the SA is invalid; S1b will run these kernels on SA arrays read from a possibly corrupt container (REVIEW-S1-0 MAJ-1). The ADR plans `GC.AllocateUninitializedArray` (ADR-002 section 3): any read-before-write becomes run-to-run nondeterminism, and no test fed the reference an arbitrary initial buffer before this review.
* **Why it matters.** After 1o.1 a wrong index is silent heap corruption or a wrong-but-plausible SA; the differential tests then detect it only when the corrupted value is observed.
* **Fix (tests before the first unsafe line, section 6):** a checked-pointer build of every kernel (`ESA_BOUNDS`: one `Buf<T>` struct with a bounds-asserting indexer compiled to a raw pointer in Release), guard-band (canary) buffers around SA/types/Phi in the equivalence tests, uninitialised/poisoned buffers (added for the reference: `SuffixArrayBuild_DoesNotDependOnTheInitialContentOfTheBuffer`), invalid-SA memory-safety test (added: `ComputePlcp_OnAnInvalidSuffixArray_NeverReadsOutsideTheText`), n = 0 and n = 1 through every entry (a `fixed` over an empty array is a null pointer; the text is empty when n = 0, only SA has one element).

### MAJ-2 The acceptance rule is not decidable across sessions
* **Claim.** PROCESS.md:26-29: accept an iteration if the 10 Mbp SA+LCP time improves by >= 3 % (median of 5, quiet machine).
* **Evidence.** Identical binary, `dna_10m`, 11 fresh-process runs: 1.362-1.494 s (range 9.4 % of the median, sd 3.2 %); session medians 1.463 vs 1.382 (**5.9 % apart**); within the quiet session sd = 1.7 %, so the standard error of a difference of two 5-run medians is about 1.3 %: a true 3 % gain is about 2.3 sigma inside one session and below one sigma across sessions. The LCP phase alone spread 0.30-0.40 s. libsais itself ran 2x slow for five consecutive runs at the start of session 1.
* **Why.** An iteration can be accepted or reverted by chance; "do not stop while something can be improved" turns into noise chasing.
* **Fix.** Protocol amendment: (1) A and B binaries are timed **alternately in one session** (A,B,A,B...), at least 9 pairs, the statistic is the median of the pairwise ratios with a bootstrap 95 % interval, accept iff the lower bound is above 0.97 and the median ratio below 0.97; (2) an A/A calibration run (same binary twice) precedes the first iteration and its interval must contain 1.0; (3) the first three minutes after a build or test run are discarded (load < 0.1); (4) report user+sys CPU and the steady-state row next to the cold row (cold and steady move differently when the JIT behaviour changes, R8); (5) a libsais run at start and end remains the drift control (it caught the disturbance here).

### MAJ-3 The S1b size and memory arithmetic is DNA-only
* **Claim.** PROGRESS-S1 / ADR-001 / ADR-003: "Core 10.4, Full 14.8 B/char, gate <= 16"; ADR-002 section 3: peak 12-17 B/char of the Full pipeline.
* **Evidence.** The compact-LCP rule ends in U32 whenever most LCP values exceed 65,535: measured above for `a^n`, `abab`, Fibonacci and Thue-Morse at 10 Mbp: index (SA + LCP + text) = **9.00 B/char** instead of 6.0; with the child table (4) + ISA (4) + RMQ (0.4) of ADR-003 the Full profile would be **17.4 B/char > 16**. The peak RSS of SA+LCP alone is already 18.5 B/char (VmHWM, 19.3 by wait4) on these texts; the ISA of the navigation pack adds 4 B/char, so about 22.5-23.3 against the 24 gate with no slack for the optimized kernels' own temporaries. `rep_10m` is U16: Full about 15.4, inside.
* **Why.** The gate is stated for random DNA (so it is not violated), but PLAN/ADR text reads as a universal bound, and the repeat-rich inputs a suffix tree is bought for (genomes with long repeats, pangenomes, S2 target) sit between the measured corners.
* **Fix.** State in ADR-003 / PLAN that the 16 and 24 B/char gates apply to the gate corpora and publish the measured corners above as a table; decide in S1b whether to add a 3-byte or variable-length LCP tier (the arrays of `a^n`/Fibonacci are extremely compressible) or to accept U32 for such texts; measure a genome-like repeat-rich text (real chromosome, not `rep_10m`) before fixing the container's LCP kinds.

### MINOR
* **MIN-1 The naming-equality predicate is protected by one test.** M10 (type comparison removed) and M11 (virtual-$ case returns `true`) are each killed by exactly one test, `LmsSubstringEquality_MatchesTheDefinition_OnAllSmallStrings` (1 failing test of 164); the SA tests, the 4.4 M fuzz cases of the Log and the 79 libsais vectors do not see them. Confirmed: the dedicated predicate test really kills the known survivor. The optimized naming (libsais-style length array + word compare) will not call `LmsSubstringsEqual`; the same definition test must be re-pointed at whatever replaces it (section 6, T2).
* **MIN-2 Six input-validation gaps (M40, M41, M50, M51, M58b, M60)** survived all four categories: an oversized suffix-array buffer accepted by `Build(span)` and by `ComputePlcp` (`!=` weakened to `<`, `SaisReferenceOfT.cs:66`, `LcpReferenceOfT.cs:61`), `CompactLcp.Builder` accepting fewer escapes than announced / a repeated escape rank / length 0, a negative alphabet size accepted on the span overload. Fixed by added tests (`ReviewS1aTests`).
* **MIN-3 The "no recursion when all names are distinct" property is untested (M08).** `names <= m` instead of `names < m` gives the same SA with one useless recursion level per call; invisible to every equality test. Added `AllLmsSubstringsDistinct_NeedNoRecursion` (trace depth 1 on `AllDistinct`). The optimized kernels must keep the trace-level equivalence (levels, `m`, `names` per level) in their differential test, otherwise a performance bug is invisible.
* **MIN-4 75 of the 79 libsais vectors need no external file** (generated families), yet `Vectors` is `[Explicit]`; the default run therefore has no libsais-hash protection of the oracle. Suggest a default-run subset (37 adversarial families at 10^5, about 1-2 s) and keep the full set explicit.
* **MIN-5 Wall-clock assertions in the default suite.** `PhaseTraceTests.Phases_AreTimedPerLevel_AndAccountForTheBuild` asserts `sum > saisTicks / 2` and `lcpSum > lcpTicks / 2` on a 400k build; not flaky in any unmutated run I did, but it will be on a loaded CI machine or a faster kernel whose allocation share grows. Move it to the explicit Performance category or drop the lower bounds.
* **MIN-6 Stale test comment.** `DifferentialFuzzTests` says "about 4 minutes at the acceptance sizes"; measured 24 s (seed 1, 1,101,000 cases).
* **MIN-7 `CompactLcp.Builder` shares its arrays with the built instance** and `Set` still works after `Complete()`, so a published `CompactLcp` is not immutable (`CompactLcp.cs:248`, `Builder.Set`). Harmless today; the S1b container writer and the shared index assume immutability. Seal the builder in `Complete()`.
* **MIN-8 `SaisTrace`/`LcpTrace` are not thread-safe and sit in the kernels' hot path** (`trace?.End` per phase, one `long[12]` per level). Fine for the reference; the optimized kernels should take the trace as a generic struct parameter (`TTrace : struct`, `NoTrace` compiled out) so that the profile build and the production build are one source.
* **MIN-9 The size guard in `TextPreparation.Prepare` (M48) is not testable at test scale** (needs a 4 GB text span); `EnsureTextLength` itself is tested at the boundaries. If wanted, expose the guard as `PrepareCore(long length, ...)` for a fake-length test. Also unchanged from REVIEW-S1-0 MAJ-7: the ESA limit `Array.MaxLength - 1` still differs from `SuffixTreeLimits.MaxTextLength = int.MaxValue / 2`.

## 4. What I verified correct (with evidence)

1. **Reproduction**: section 1; 164 + 6 + 79 + 3 + 494 + 672 + 137 tests, vectors 79/79, 21 benchmark builds all `vector_match = 1`, two extra fuzz master seeds with 2,202,000 cases and 0 mismatches.
2. **Correctness arguments I re-derived and the tests agree with:** (a) head/tail disjointness of the recursion buffers: `m <= (n - 1) / 2` (LMS positions lie in [1, n-2], pairwise >= 2 apart), so `2m <= n` and `SA[0..m]` and the tail `[n+1-m, n]` never overlap; (b) name slot `1 + m + (pos >> 1) <= n` (maximum `n` only for the variant of M43, the original has one slot of slack); (c) every `ToInt/FromInt` and index expression is `<= n + 1 <= Array.MaxLength = 2,147,483,591 < int.MaxValue`, so no int overflow at the limit (`16 * escapes8` is `long`, `PayloadBytes` is `long`, the guard `textLength >= Array.MaxLength` has no `n + 1`); (d) the PLCP loop keeps `j + l <= n` (Kasai) so `text[j + l]` is read only after the bound; (e) SA-IS recursion depth <= floor(log2 n) + 1 <= 31 frames, each frame small (`ref struct` generics, no stackalloc in the recursion), so no stack risk, and the per-level arrays form a geometric series; (f) n = 0, 1, 2 handled (`Sais` returns after `sa[0] = n`; tests `KnownExamples`, adversarial sizes 0-5), sigma = 1, UTF-16 alphabets up to 65,536 symbols (width `ushort` from 257 symbols, `MapWords = 1024`, M36/M38 killed), lone surrogates, U+0000, U+FFFF (`Utf16Texts_AreSortedByCodeUnit`, vectors, fuzz family `unicode-mix`). Order is UTF-16 **code unit** order, not code point order (U+E000 sorts after a surrogate pair's high surrogate); pinned by the added `OrderIsByUtf16CodeUnit_NotByCodePoint`, and it is the same order the Ukkonen tree and libsais16 use.
3. **Thread safety and determinism:** no mutable static state (`grep` of `static` fields: only `Empty => NegativeOne`), no `Random`, no parallelism; the added `ConcurrentBuilds_OverASharedPreparedText_AreIdenticalToTheSerialBuild` builds four texts 12 times each on 4 threads and compares SHA-256 of SA and LCP with the serial build. Safe to share a `PreparedText` between threads; not safe to share one `SaisTrace`.
4. **Oracle independence:** `SuffixArrayVerifier` does not use any construction code; the libsais vectors come from an independent implementation; naive SA/LCP are definitional.
5. **The n+1 layout** (`SA[0] = n`, buckets from 1, `LCP[0] = LCP[1] = 0`, libsais `LCP[i] = our LCP[i+1]`) is consistent in code, tests, harness hash and manifest.

## 6. Plan for 1o.1 (first three optimization iterations)

**Reality check on the targets** (all from the Log profile, dna_10m, warm build 1.289 s: prepare 2.6 %, SA-IS 73.9 %, LCP 22.7 %; libsais same session: SA 0.32 s, PLCP + LCP 0.235 s). The LCP phase is **already within 1.3x of libsais** (0.313 s vs 0.235 s), so the whole LCP kernel can gain at most about 0.08 s (5-6 % of the total); the 2.5x gap to libsais is **3.3x in SA-IS** (1.03-1.05 s vs 0.32 s). The ADR estimate "R1 = 1.2-1.5x on 70 % of the build" gives 1.1-1.25 s; I expect the three iterations below to land at about 1.05-1.2 s (-15 to -25 %), i.e. at the ceiling goal 1.0 s only with R2-R5 afterwards, and the 0.62 s stopping bound will not be reached by R1 (UNVERIFIED estimates, not measurements). The 3 % bar is 0.042 s.

**Step 0, before any optimization (tests and tooling only, one or two commits, no acceptance bar):**
* **T0 memory-safety net (MAJ-1).** A `Buf<T>` pointer wrapper with `#if ESA_BOUNDS` asserting indexer (Release = raw pointer); a Debug/`ESA_BOUNDS` run of the whole Esa test project as a CI configuration; canary guard bands (e.g. 64 ints/bytes before and after SA, types, Phi, text, filled with a poison pattern, checked after every build) in the kernel equivalence tests; build with SA/Phi buffers filled with several garbage patterns (added for the reference, to be run for every kernel); n in {0, 1, 2, 3} through every entry point including the empty-text pointer.
* **T1 kernel registry.** `KernelEquivalenceTests` parameterised over a list of engines (`Reference` now, `Fast` later): SA, LCP (kind, escape count, all values) and the `SaisTrace` levels (`n`, sigma, `m` per level) must equal the reference on exhaustive (binary <= 18 in the default run, <= 22 explicit), the 38 adversarial families at n = 2000 and 10^5, `all-distinct` 65,536, and fuzz with the reference as `reference` argument of `FuzzOracle.Check` (the hook exists).
* **T2 predicate re-pointing.** The definition test for LMS-substring equality takes a delegate; the kernel's naming comparison (whatever form it takes) is run through it on the same 222,332 pairs. The mutants M10, M11 and M08 are re-run against the kernel (`run_mutants.py --kernel`, patterns adapted) as an acceptance step of the naming iteration.
* **T3 JIT check.** A script that runs `DOTNET_JitDisasm=<method>` for the kernel methods and fails on `CORINFO_HELP_RNGCHKFAIL` (ADR-002 R1).
* **T4 A/B runner.** Committed script for the interleaved paired protocol of MAJ-2, with the A/A calibration result in the Log.
* **T5 libsais subset in the default run** (MIN-4), so the oracle itself is protected in every run.

**Iteration 1 (1o.1a): LCP pointer kernel** (`int*`/`byte*` Phi, PLCP, pass 3; escape counting fused into the PLCP loop; 8-byte word compare with a tail loop that never reads `text[n]`; compact-LCP builder written through pointers; no generic `ToInt`/`FromInt`). Expected: LCP 0.313 -> about 0.24 s (the libsais PLCP+LCP floor is 0.235 s), i.e. -0.07 s = **-5 %** of the total. Risk: **low** (independent oracles Kasai/naive; short loops; first user of T0, so also the shake-out of the infrastructure). Tests that must exist first: T0, T1 (LCP part), `ComputePlcp_OnAnInvalidSuffixArray_NeverReadsOutsideTheText` and the escape tests (254/255/256, 65,534/65,535/65,536, selection boundaries) already exist; mutants M21-M28, M55 re-run on the kernel. May stay below 3 % if memory-bound: then it is reverted by the rule and recorded, which is a legitimate outcome.

**Iteration 2 (1o.1b): the linear SA-IS passes at every level** (symbol count, type classification, LMS counting, placement of LMS suffixes, compaction of the sorted LMS positions and of the names, the reduced-problem bookkeeping and the SA-tail translation): about 33 % of the build; pointer loops over pinned arrays, `bool[]` -> `byte*`, readers as pointer structs (`byte*`, `ushort*`, `int*`), int-only, same algorithm and same buffer layout (no R6). Expected: -20 to -30 % of that block = **-0.09 to -0.14 s, 6-10 %**. Risk: **low to medium** (simple loops but they carry the layout invariants: `2m <= n`, name slot `<= n`, tail disjointness). Tests first: T0 guard bands on SA/types/tail, T1 incl. trace equality, the uninitialised-buffer test, mutants M14-M20, M43 (zero-slack variant must be killed by the guard band, not by luck), M45-M47 for equivalence.

**Iteration 3 (1o.1c): the four induction passes and the naming loop** (about 40 %: induction 30 %, naming 10 %): hoisted locals, bucket cursors as `int*` (`stackalloc` only when sigma <= 256; recursion levels have up to n/2 buckets and must use the pinned workspace), types as `byte*`, no checked conversion; naming keeps the reference algorithm for now (the length-array rewrite is a later, separately accepted step because it changes the equality predicate). Expected: -15 to -25 % of the block = **-0.08 to -0.14 s, 6-10 %**. Risk: **medium** (the core of SA-IS; every bucket write is an unchecked store). Tests first: everything above plus T2, the exhaustive run on the kernel (binary <= 22, ternary <= 13, 4-ary <= 11, about 1 minute), Vectors 79/79, Fuzz with >= 3 master seeds against the reference at 10^6 / 10^5 / 10^3 cases, mutants M01-M09, M17, M20 on the kernel.

**Order rationale.** 1 is the safest and builds the infrastructure on the one component whose floor (libsais) is known; 2 is mechanical and large enough to clear the bar; 3 is the hardest and gets the strongest net. If iteration 1 is rejected (< 3 %), keep the kernel only if it is not slower and simplifies nothing else; the next candidates after these three are R2 (prefetch; likely small at 10 Mbp on this 480 MiB-L3 VM, to be judged at 50 Mbp), R4/R5 (sigma <= 4 fast path, radix first pass) and the naming rewrite.

**Keeping `SaisReference` the permanent oracle.** (1) Never edit `SaisReference.cs`, `SaisReferenceOfT.cs`, `LcpReference*.cs` for speed; the kernels live in new files (`SaisKernel.cs`, `LcpKernel.cs`) behind the same entry-point shape, selected by an internal enum, so the reference is also the fallback where `unsafe` is disallowed. (2) Protect the oracle with oracles that do not depend on it: naive SA/LCP, `SuffixArrayVerifier`, Kasai, the libsais hashes (T5), and an optional tripwire test that pins the SHA-256 of the four reference source files and fails with a message "the oracle changed: re-run mutation set and get review" when they change. (3) Keep the mutant list (`analysis/mutation/mutants.json`) as an acceptance artefact: after each kernel iteration the same mutants, mapped to the kernel source, must be killed by the equivalence tests (a differential test that cannot see a mutant of the kernel is too weak). (4) Every kernel is compared with the reference **and** with the independent oracles (so a bug copied into both is still caught), and fuzz keeps `reference` as an argument, not a hard-wired default.
