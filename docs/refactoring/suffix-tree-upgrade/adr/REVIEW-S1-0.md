## MAJOR

### MAJ-1 Container validation rules do not match the goal "closes the v6 weakness"
* **Claim.** ADR-003 section 6: `Checked` access "clamps/validates every index read from SA, ISA, CHILD, LCP_OVERFLOW against its section bounds ... closes the weakness"; Header level checks "`COUNT * ELEM_WIDTH == LENGTH`", "every section inside the file". Section 9: "All accessors check `ObjectDisposedException` at the public boundary only".
* **Evidence.** S0 has just fixed the same bug class in v6: `offset + size > _position` wrapped near `long.MaxValue` and the mapped provider dereferenced the result (`Persistent/MappedFileStorageProvider.cs:233-247`; original form at `b0922125`, lines 235 and 243; commit `bd680f86`). The SESA fields are untrusted 64-bit values: `COUNT` (u64) times `ELEM_WIDTH` (u32), `OFFSET + LENGTH`, `rank * POS_WIDTH + base` all wrap. "Clamp against section bounds" says nothing about termination: `nextlIndex`/up/down chains of the child table and parent climbs can cycle on a corrupt file (S0's validator explicitly checks cycles). Text reads are derived (`text[SA[i] + depth]`, ADR-001 section 3) and must be bounded by `TEXT_LEN`, not by the SA section; a corrupt LCP can make `depth` exceed the suffix length. The disposed check at the public boundary is check-then-use: unmapping under a running reader is an access violation (v6 has the same pattern, `Persistent/PersistentSuffixTree.Diagnostics.cs:91-96`). A file truncated by another process after the mapping exists raises SIGBUS on Linux, not an exception. The dispatcher reads the magic with one handle and maps by path afterwards (TOCTOU).
* **Why.** A mmap reader over untrusted files is exactly the weakness ADR-003 says it closes; as written, the first implementation would reproduce the S0 bug and add hang risks.
* **Fix (into ADR-003 section 6/9).** (1) All arithmetic on file-controlled values in `checked`/`UInt128` or subtraction form (`(ulong)i < (ulong)count`). (2) Every loop over file-controlled links has a progress invariant (strictly increasing index bounded by `rb`) or an iteration cap. (3) Derived text reads bounded by `TEXT_LEN`. (4) State the guarantee: with `Checked`, a corrupt body gives `InvalidDataException` or a wrong-but-memory-safe answer, never a crash or hang; tamper detection comes only from `Sections` (CRC-32C is not cryptographic), `Structure` and `TEXT_SHA256`. (5) Reader reference count (`SafeHandle.DangerousAddRef` or an `Interlocked` counter) or a documented "Dispose must not overlap readers" rule; an `OpenMode` that reads into managed memory for untrusted or removable media. (6) The SESA reader re-validates the magic from the mapped header (dispatcher read is advisory). (7) The writer sets `HAS_CRC` on every section by default, otherwise the `Sections` level checks nothing. Tests in the S0 style (byte-flip fuzz) plus targeted wraps: `COUNT = 2^63`, `ELEM_WIDTH = 2^32-1`, `OFFSET = u64.Max - 3`, a CHILD cycle, files of 0, 7, 4095 and 4096 bytes.

### MAJ-2 1b.7 acceptance "Structure level catches body corruption" is false
* **Claim.** PROGRESS-S1.md row 1b.7: "flip every byte of header + section table, and 10^3 random body bytes: `Header` level catches header corruption, `Structure` level catches body corruption, never a crash or hang or out-of-mapping read". ADR-003 section 6 lists what `Structure` checks.
* **Evidence.** The listed Structure checks (permutation, recomputed LCP, adjacent-rank order, child round trip, ISA inverse, "RMQ spot checks") do not cover `BUCKET`, `NEXTSYM`, `ALPHABET`, `NODE_COUNT`, `LRS_*`, and RMQ only by spot check, so flips there pass. More importantly, a flipped `TEXT` code unit can leave SA and LCP valid for the *modified* text. Experiment (Python model of the stored arrays and of the Structure checks): for random DNA (n = 50, 200, 1000: 150, 600, 3000 substitutions) and a 20-letter alphabet (19,000 substitutions) every substitution was caught, but for the plan's own family "all-distinct symbols (sigma = n)" (PROGRESS-S1.md, test strategy) flipping the low bit of any one of 200 code units passed every check (200 of 200), because the SA of an all-distinct text depends only on symbol ranks.
* **Why.** The acceptance can fail at random or be silently weakened ("not detectable by design"), which PROCESS rule 4 forbids.
* **Fix.** Split the acceptance by level. `Header`: every flip in header and used section-table bytes is rejected (CRC), padding and unused slots are explicitly out of scope or checked for zero. `Sections` (with `HAS_CRC` on every section): 100 % of single-byte body flips rejected (CRC-32C guarantees this). `Structure`: no crash/hang/out-of-mapping read for every flip, and every flip is either rejected or yields an index whose answers equal an index rebuilt from the *stored* text (differential). Add `BUCKET`/`NEXTSYM`/`ALPHABET`/header-statistics recomputation to the `Structure` list, or state that they are covered only by CRC.

### MAJ-3 RMQ/PSV/NSV helper: time and memory are not as stated
* **Claim.** ADR-001 section 5 (c) and R-SL: "`p = RMQ(a+1..b)`, `L = PSV_strict(p)`, `R+1 = NSV_strict(p)`: O(1) with a sparse table over blocks, O(block) otherwise ... about 0.3-0.5 B/char". ADR-003 section 5: RMQ about 0.4, Full about 14.8, +NEXTSYM about 15.8 "still <= 16".
* **Evidence.** The method is correct (it returned the right link in every tested case, see "Verified"). The cost figures do not follow from the description. A sparse table over `n/B` block minima has `(n/B) * (floor(log2(n/B)) + 1)` entries. At n = 10^7 with 4-byte entries: B = 32 gives 2.5 B/char, B = 64 1.19, B = 128 0.56, B = 256 0.27, B = 512 0.13. So 0.3-0.5 B/char needs B in about 128-256, and then every query scans up to 2B LCP bytes in the blocks at both ends. Finding the previous/next position with a smaller value is not O(1) with block minima: it is O(B + log(n/B)) (binary lifting on the sparse table), or O(n/B) without lifting. With Full about 14.7-15.0 B/char, `NEXTSYM` brings it to 15.7-16.0: no margin, and `rep_10m`-like inputs (escapes, see MIN-14) reach or exceed 16. Compact LCP: "scan while `LCP >= t`" cannot be decided from the byte `255` when `t >= 255`; every escaped entry needs a lookup in the overflow list (binary search; ADR-002 section 4).
* **Why.** The P1 decision rule (">600 ns median -> evaluate O1", "choose (c) unless ...") and the Full-profile gate arithmetic are built on these numbers.
* **Fix.** In ADR-001 section 5 / ADR-003 section 5 replace the O(1) claim by O(B + log(n/B)) and the memory by the table above; make P1 sweep B in {64, 128, 256}; state that the helper also works on the compact LCP only through a cursor/lookup for escapes; keep `NEXTSYM` outside the 16 B/char argument or measure it first.

### MAJ-4 The single-array child table is gate-critical and unverified; the fallback is not a decision
* **Claim.** ADR-003 section 4 (CHILD, 4 B/char, packing UNVERIFIED), PLAN.md:83 "child 4", P3 in ADR-001 section 5.
* **Evidence.** Core 10.4 B/char and Full 14.8 B/char (arithmetic verified, see "Verified") rest on 4 bytes per rank for `up/down/nextlIndex`. With three plain 4-byte arrays the child table is 12 B/char, Core becomes 18.4 and Full 22.8 B/char, far over the 16 B/char gate that the owner put on Full (PROGRESS-S1.md answer 1). The published single-array packing needs LCP comparisons on every read to tell the stored field kinds apart (details not checked here); with the compact LCP those reads cost an escape check (MAJ-3). P3's decision rule only says when to *replace* the child table by the RMQ-only variant (">= 1.5x faster on count and smaller"); it does not say what happens if the 4-byte packing turns out impossible or slower. Also, ADR-003 section 4 said the layout is fixed in "WP 1b.2" while PROGRESS-S1.md puts the child table in 1b.1 (corrected, see "Edits").
* **Why.** If the packing fails after the file format is frozen, the Full profile cannot meet its gate and the format has to change.
* **Fix.** Make P3 the *first* experiment of 1b.1 (before the container layout is relied on) and add a rule: if the single-array child table is not <= 4.1 B/char and within 20 % of the 3-array reference on count, adopt the RMQ-only structure (it is needed for suffix links anyway, about 0.3-0.6 B/char) as the navigation structure and drop `CHILD` from Core; record the owner-visible consequence for the 16 B/char gate.

### MAJ-5 P4 is run at the wrong stage, on the wrong code, with a threshold at the noise floor
* **Claim.** ADR-002 section 2 item 6 and PROGRESS-S1.md row 1a.5: the `int` instantiation of kernels generic over `TIdx : unmanaged, IBinaryInteger<TIdx>` must be within 3 % of a hand-written `int` clone of the induce loops, measured by a micro-benchmark in 1a.5.
* **Evidence.** At 1a.5 the only kernels are the safe `Span` ones (`SaisReference`, row 1a.3); bounds checks and memory latency dominate there, so generic-math overhead is hidden. The overhead matters on the R1 pointer kernels (1o.1), where the loop is lean, and on the whole method after inlining (large generic methods can exhaust the JIT inlining budget; this is only visible on the full build). A 3 % threshold equals the acceptance bar of PROCESS.md:26-29 and is close to run-to-run noise of a managed 10 Mbp build, so "within 3 %" is not decidable with 5 runs. The long path is S2 work (ADR-002 section 2 item 7); genericity is paid for in S1.
* **Why.** A late "P4 failed" after R1 means rewriting the optimized kernels.
* **Fix.** Run P4 twice: at 1a.5 (design smoke test) and again immediately after 1o.1 on the pointer kernels, on the full SA build time (5 fresh processes, 10 Mbp), with an explicit rule (for example "accept if the 95 % interval of the ratio is below 1.05, else switch to template generation"). Consider deciding for template generation (or `int`-only kernels plus a generated `long` copy in S2) now; the owner's decision is "positions are `long` in the contract", not "kernels are generic".

### MAJ-6 1b.6 acceptance cannot fail
* **Claim.** PROGRESS-S1.md row 1b.6: "re-run the existing `ISuffixTree`-level assertions through a backend factory in new test classes (first inventory which existing tests build `SuffixTree.Build` directly; originals are not edited)"; acceptance "all backend-agnostic assertions pass for ESA".
* **Evidence.** "Backend-agnostic" is chosen by the implementer after the inventory; an assertion that fails for ESA can be classified as backend-specific. The existing suites have 494 + 576 + 103 tests (PROGRESS-S0.md log, WP 0.3); `tests/SuffixTree` has 396 `SuffixTree.Build(` call sites and 67 files that build a tree directly or through `PersistentSuffixTreeFactory`.
* **Why.** This package is the main regression net between the existing behaviour contract and the new backend.
* **Fix.** Pre-register: the inventory (test id, adapted or excluded) is committed *before* the first ESA run; every exclusion has a reason from a closed list (tests the Ukkonen internals, persistence format v6, performance guard, node-object identity); the reviewer checks the exclusion list; the log reports N total, M adapted, K excluded.

### MAJ-7 Size-limit policy is inconsistent and `NodeCount` can overflow silently
* **Claim.** ADR-001 section 7: `n > int.MaxValue - 1` throws `NotSupportedException` "never overflows silently"; section 8 the same bound; ADR-002 section 2 item 7: `n + 1 <= 2,147,483,591 (Array.MaxLength)`.
* **Evidence.** Three different limits. The existing library-wide rule is `SuffixTreeLimits.MaxTextLength = int.MaxValue / 2 = 1,073,741,823` because the terminated tree has up to `2n + 1` nodes and `NodeCount` is an `int` (`Core/SuffixTreeLimits.cs:22`, S0 WP 0.2; K0 gap `docs/refactoring/suffix-tree-upgrade/analysis/audit/K0_gaps.md:23`). The ESA `NodeCount = 1 + I + (n + 1)` with `I <= n - 1` reaches `2n + 1` (for example for `a^n`), so for `n` in (1,073,741,823, 2,147,483,590] the facade property overflows silently although the arrays still fit. `ThrowIfTextTooLong` exists in Core for exactly this.
* **Fix.** One policy in ADR-001 sections 7/8: the `int` facade either calls `SuffixTreeLimits.ThrowIfTextTooLong` like the other backends, or computes `NodeCount` in `long` and throws when it exceeds `int.MaxValue`; the engine limit for the `long` API is `Array.MaxLength - 1`. Test with a fake reader (no allocation) at 1,073,741,823 / 1,073,741,824 / 2,147,483,590 / 2,147,483,591.

## MINOR

### Design and specification
* **MIN-1 Suffix-link edge conventions and contract gaps.** Formula and cases are correct (see "Verified"), but the implementation must fix: `PSV` of nothing = 0 and `NSV` of nothing = n + 1 for `t = 0` (depth-1 nodes link to the root); `Psi(lb) = 0` when `SA[lb] = n - 1`; `LCP[n + 1] := 0` in `max(LCP[lb], LCP[rb + 1])` for the parent depth; `ParentDepth(root) = 0`, `LengthOf(root) = 0` (MEM, `SuffixTreeAlgorithms.cs:213`, and `MatchLocus` `:417` rely on it). `ISuffixTreeNavigation.TrySuffixLink` on a leaf or on an implicit locus is undefined in the contract (the formula gives the `Psi` leaf for a leaf; for an implicit locus the target interval needs a threshold search, not the strict-PSV recipe). Add tests: depth-1 nodes, `SA[lb] = n - 1`, terminator-member intervals, rank 0.
* **MIN-2 `n = 0` is a special case.** ADR-001 section 4 says "no virtual-root special case exists"; for `n = 0` the root `[0..0]` is a singleton. The model emitted the leaf-shaped event `(0, -1, 1, 0, 0)` while Ukkonen emits `(0, 0, 0, 0, 0)` (`SuffixTree.Diagnostics.cs:11` returns early, root `LeafCount` is never set; `Traverse` then visits only the root) and `NodeCount` is 1, not 2. 1b.1 lists "n = 0" but not the expected values: add them (also `PrintTree` = header + `0:ROOT`, `DiagnosticsContractTests.cs:8-22`).
* **MIN-3 H-OCC status.** True (proof and experiment in "Verified"). Keep the planned test, but it needs no `Traverse` of the real engine: a test-only naive ESA model (SA, LCP, `min(SA[lb..rb])`) compared with `CalculateLogicalHash` of the Ukkonen tree can run right after 1a.1, before any ADR text depends on the answer. What breaks if it were false: only `CalculateLogicalHash(esa) == CalculateLogicalHash(ukkonen)`, the serializer `Export`/`Import`, and the `Traverse` stream differential (1b.1, 1b.8); no library consumer of `Traverse` needs the leftmost occurrence (ADR-001 section 4 is right about that).
* **MIN-4 Navigator contract details missing from ADR-001 section 3.** `CollectLeaves` must **append** (`FindAllLcs` calls it repeatedly on one list, `SuffixTreeAlgorithms.cs:68-71`; persistent navigator `PersistentSuffixTreeNavigator.cs:149`, `:209`). `FindAnyLeafPosition` must return -1 for the empty-suffix leaf (Ukkonen `SuffixTree/SuffixTree.Algorithms.cs:239`); the ADR's "`SA[lb]`" would return `n`. `GetChildren` of a leaf is empty. `TNav` is constrained to `struct` (not `allows ref struct`), so the navigator cannot hold `Span`/`ReadOnlySpan` fields; it needs arrays or pointers (ADR-003 section 4's "wrap the mapping as `ReadOnlySpan<T>`" applies to the engine, not to the navigator). The number of `GetChildren` calls is not bounded by the query (MEM visits all siblings along the path); only link calls are (`<= 2|query|`).
* **MIN-5 The ESA text object (`ITextSource`) is not specified.** `ITextSource.Slice` returns `ReadOnlySpan<char>` (`Core/ITextSource.cs:38`); a text stored as bytes (codecs 1 and 2) cannot alias it. `SuffixTreeSerializer.WriteTextCodeUnits` calls `Slice(offset, 4096)` (`Persistent/SuffixTreeSerializer.cs:209`), so `CalculateLogicalHash(esa)`, the strongest oracle of 1b.1, needs it. Decide: allocate per call, or a documented per-thread scratch. Codec 2 (dense remap) also needs an ALPHABET lookup in `GetEdgeSymbol` and `TryGetChild(key)` because the generic code passes raw query chars; state that cost.
* **MIN-6 Assembly layout and API clashes.** `SuffixIndexFactory.Open` must call `PersistentSuffixTreeFactory` and `EsaSuffixTree`, so it needs a project that references both (ADR-001 section 6 lets `SuffixTree.Esa` reference only Core). `EsaSuffixTree : ISuffixTree, ISuffixIndex` has two `Text` members with different types (`ITextSource` vs `IIndexText`): one needs an explicit implementation. `SuffixTree.Core` builds with `GenerateDocumentationFile`, `TreatWarningsAsErrors` and `AnalysisLevel latest-all` (`Core/SuffixTree.Core.csproj:7-10`), so every new public member needs XML docs and every `latest-all` rule applies to the unsafe kernels while PROCESS.md rule 4 forbids `#pragma` suppression: decide whether `[SuppressMessage]` with a justification is allowed. The interface sketch has `IndexOperation.Lca` but no `Lca` method (`ISuffixArrayAccess` has `Lcp` only); PLAN.md:74-76 lists LCA.
* **MIN-7 `PrintTree` is part of `ISuffixTreeDiagnostics` and is not in ADR-001.** The existing contract is structural (`DiagnosticsContractTests.cs:23-52`: one line per node, 2 spaces per depth, leaf lines = `LeafCount + 1`, sorted first level; the parser strips ` -> [x]` link marks). Reproducing the link marks needs the navigation pack. State that the ESA `PrintTree` follows the structural contract and that 1b.8 compares it by parsing, not by string equality.
* **MIN-8 Child lookup cost for large alphabets.** `TryGetChild` is a linear scan of up to sigma' children with two dependent reads each (ADR-001 section 4 table); the generic code calls it per query character and per rescan step. For UTF-16 texts with thousands of distinct symbols the root and shallow nodes have that many children. 1b.2's gate runs on DNA only. Add a `prot_1m` and a wide-alphabet corpus to the throughput measurement, and plan binary search over children (via `NEXTSYM`) for nodes above 16 children.
* **MIN-9 SA-IS specification details (ADR-002).** (a) Sentinel wording: item 1 says "virtual smallest sentinel, never stored" and "natural output of SA-IS with an explicit sentinel suffix". Say precisely: the kernels work on `SA[1..n]` (n entries, virtual sentinel, as sais-lite/libsais), the driver writes `SA[0] = n`; recursion levels have no extra slot. (b) Section 3 estimates `names ~ 0.9 m` for random DNA; measured with a model of the definition: m = 0.29 n and names = 0.06 m (n = 10^5), 0.015 m (n = 10^6) for DNA, 0.46 m for 20-letter protein, 0.006 m for the repetitive model. The bound (2.0 B/char) stands, the estimate (1.2) is too high by more than an order of magnitude for DNA; it also means the level-1 string of DNA already has < 65,536 names (R9 applies at once). (c) Phase D "the work buffer may hold ISA" contradicts phase C (the work buffer then holds the child table, which is a final section): Full needs a second 4 B buffer, giving 16.4 B/char with the string held (the table says 16.5, consistent). (d) R4 (sigma <= 4 fast path) applies only to texts that remap to at most four symbols; real genomes have N and soft-masked lowercase (sigma 5-10), so the gain on `dna_10m` does not transfer; add a sigma = 5 and a sigma = 10 DNA row.
* **MIN-10 Test-plan details.** (a) "Exhaustive" small strings (binary up to length 14) may not reach third-level SA-IS recursion; add an instrumented "maximum depth reached" counter to the exhaustive run and require depth >= 4 somewhere, or extend binary to length 20 (2.1 M strings in total, seconds with the reference). (b) Recursion-depth acceptance "<= 24 on n = 10^6" is vacuous: every level at least halves (`m <= n/2`), so at most `ceil(log2 n) + 1 = 21` frames occur; assert that bound and the halving per level. (c) Add targeted boundary generators for R9 (`names` = 65,535/65,536/65,537), compact-LCP escapes (254/255/256 and 65,534/65,535/65,536), n = 2^16, 2^16 +- 1. (d) The naive oracle at n <= 2000 for 10^5 cases is only feasible with ordinal span comparison (`CommonPrefixLength`/`SequenceCompareTo`); with a per-character loop the periodic families cost about 4 x 10^7 steps per case. Require ordinal comparison (UTF-16 code unit order, not culture). (e) 1a.9's "index size of SA+LCP+text <= 16 B/char" cannot fail (about 6 B/char); drop it or move it to 1b.9 where the child table exists. (f) Add: concurrent first use of the lazily built navigation pack (race), `Dispose` twice and use-after-dispose (`DisposeBehaviorTests` exists for v6), no leak with `NativeMemory`, `Locate` paging (`skip` beyond the count, empty span), `Traverse` on `a^n` with n = 10^6 (stack depth), `BUCKET` boundaries (MIN-13), pattern characters absent from the alphabet with codec 2.
* **MIN-11 Gate definitions.** (a) PLAN.md:81 says "If it fails, stop"; PLAN.md:143 says stop when "off by more than 2x"; PROGRESS-S1.md row 1a.9 only defines PASS and >2x. State what happens between 1x and 2x (suggestion: continue with 1o only if the gap is closable by roadmap items R1-R4, with an owner-visible note). (b) PROCESS.md:28 stops when "build time <= 1.1x libsais (<= 0.36 s)" but libsais 0.328 s is SA only and the S1a metric is SA + LCP; compare `build_sa_s` with libsais, `build_total_s` with the 3.3 s gate. (c) R8 (`AggressiveOptimization` vs tiered PGO) is iteration 1o.7 but changes the baseline of every earlier accept/reject decision; run it first or re-validate R1-R6 after it. (d) The S1 gate has no MEM/MUM/anchor/LCS regression bound: the stage can pass while the operations "a suffix tree is bought for" (BENCHMARK.md:12) get slower than v6 persistent (MEM 0.163 s, MUM 0.105 s, anchors 0.0877 s, BENCHMARK.md:172-175). Owner decision: add "not slower than v6 persistent by more than 25 %" or state that it is accepted.
* **MIN-12 `Vectors` category.** Row 1a.6 says "run explicitly ... like Parity/Performance" and "fails, never skips, when inputs are missing". Parity runs in the default `dotnet test`; only Performance is `[Explicit]` (PROGRESS-S0.md log, WP 0.0). A `Vectors` test that fails without inputs would make the default run of the new project red on a clean checkout. Say: `[Explicit]`, and fail (not skip) when selected and inputs are missing.
* **MIN-13 `BUCKET` definition (ADR-003 section 4).** `COUNT = sigma^k + 1` first ranks cannot place suffixes shorter than k: a suffix such as `AC$` sorts between k-mer groups and would be counted into the previous group by `[first[w], first[w+1])`. Use `(sigma + 1)^k` buckets (terminator symbol) or verify the interval ends with one SA read. Also: the rule "largest k with `sigma^k * POS_WIDTH <= n/2`" does not terminate for sigma = 1 (`1^k = 1`) and is undefined for sigma = 0; cap k (for example 12) and compute in 64-bit/`UInt128` (sigma = 65,536, k = 2 overflows 32 bits).
* **MIN-14 Compact LCP details (ADR-002 section 4).** The representation is chosen after counting escapes, but pass 3 "writes directly into the compact LCP"; add a counting pre-pass over PLCP (sequential, about 10 ms at 10 Mbp) or a retry. `escapes * 8 <= n/2` overflows `int` above about 268 M escapes: use `long`. Random access into the overflow list is a binary search (about 19 steps for 500 k entries) on exactly the deep nodes of repeat-rich texts; measure on `rep_10m` (a 20-copy model of that input, 1 % substitutions, has 3.5 % of ranks with LCP >= 255, more with 100 copies; 8 B per escape = 0.28 B/char at 3.5 %) and consider a sampled index. The break-even of `U8+overflow` against `U16` is 12.5 % escapes (`1 + 8e = 2`), the rule's `n/2` (6.25 %) is twice as conservative; say which is intended.
* **MIN-15 Writer and format details (ADR-003).** (a) "flushed" before writing the magic must mean `Flush(flushToDisk: true)`, and again before the rename; use a unique temp name. (b) `BUILD_INFO` contains "options" and the writer's commit: serial and parallel builds differ in the thread count, which contradicts the S5 claim "byte-identical serial and parallel" (section 1); keep execution-only options out of `BUILD_INFO`. (c) `HEADER_CRC32C` covers `[0,124)` plus "the whole section table": define as `SECTION_COUNT * 64` bytes; bytes after it are outside the CRC and must be zero-checked or declared ignored. (d) The CRC includes the magic, which is written last: compute it over the final header.
* **MIN-16 `Traverse` costs.** The occurrence pre-pass needs up to `I` transient ints (0.62 n on random DNA = 2.5 B/char) and the explicit stack holds one frame per open interval, up to n frames on `a^n`. State the limits, or compute `occ` only when the visitor needs it (it cannot be known; document instead).
* **MIN-17 `CountDistinctSubstringsByLength` override.** ADR-001 section 7 says "histogram of LCP"; the count for length l is `#{ i : LCP[i] < l <= n - SA[i] }`, a difference array over `(LCP[i], n - SA[i]]`, which needs SA as well. Total: `n(n+1)/2 - sum LCP` is right (use `long`).

## Verified as correct (with evidence)

1. **Navigator completeness.** `ISuffixTreeNavigator<TNode>` has 12 members (`Core/ISuffixTreeNavigator.cs:17-69`: `Text`, `Root`, `NullNode`, `IsNull`, `IsRoot`, `GetEdgeSymbol`, `LengthOf`, `GetSuffixLink`, `TryGetChild`, `CollectLeaves`, `FindAnyLeafPosition`, `GetChildren`). `grep "nav\."` over `Core/*.cs` finds exactly these; ADR-001 section 3 lists all 12 with the right call sites (every cited line checked at tip and at `b0922125`). `parent` and node depth are never read; `currentNodeDepth` is tracked by the algorithms (`SuffixTreeAlgorithms.cs:15-19,478`). Reusing `SuffixTreeAlgorithms.*<TNode,TNav>` unchanged is feasible; the extra requirements are in MIN-4/MIN-5.
2. **Suffix-link formula.** `sl(v) = LCA(Psi(lb), Psi(rb))`, `Psi(i) = ISA[SA[i]+1]`, for an lcp-interval with depth `d >= 1`: proof: `lcp(SA[lb], SA[rb]) = d` exactly, so the suffixes at `SA[lb]+1`, `SA[rb]+1` have lcp exactly `d - 1` (with the unique smallest terminator, order of suffixes with a common first symbol is preserved by dropping it, including the case `SA[i] = n - 1` whose successor is the empty suffix, rank 0), hence `Psi(lb) < Psi(rb)` strictly, `min LCP[Psi(lb)+1..Psi(rb)] = d - 1`, and the LCA is the interval of value `d - 1` around that minimum (a branching node: the two continuations differ). Cases: `d = 1` gives the root; a member that is a suffix equal to the label (terminator child) works; singleton intervals never need it. Experiment: Python port of the C# Ukkonen builder (links set by `AddSuffixLink`) vs the formula: all links equal for every string over {a,b} up to length 10 (2,047 strings), over {a,b,c} up to 7 (3,280), over four letters up to 5 (1,365), plus 400 random/periodic/Fibonacci/run strings of length 10-60.
3. **Generic code calls the link only on internal nodes, at most once per query character per locus.** `GetSuffixLink` is called only at `SuffixTreeAlgorithms.cs:477`, guarded by `IsRoot` at `:475`; `currentNode` becomes `currentEdge` only when an edge is fully consumed (`:437-442`) and a leaf edge ends in the terminator, which no query char equals; the rescan (`:491-509`) cannot cross a leaf because the matched string excludes the terminator. Bounds: matching statistics `<= |q|`, MEM two loci `<= 2|q|` (`:245-248`), MUM `<= |q|` (`:310-311`). Experiment: the ported `AdvanceMatchingStatistics`/`TryConsumeSymbol`/`FollowSuffixLinkAndRescan` running on the ESA navigator of ADR-001 (handle `{Lb, Rb, Depth, ParentDepth}`, link by the formula, `ParentDepth = max(LCP[lb], LCP[rb+1])`) over 3,000 random/periodic/Fibonacci (text, query) pairs: matching statistics equal brute force, the leaf set below every locus equals the occurrence set, 0 link calls on leaves or on the root, maximum link calls per query character 0.98.
4. **ESA is node-for-node the Ukkonen terminated tree, and H-OCC is true.** Terminator: key `-1`, leaf `End = BOUNDLESS = -1` (`SuffixTree/SuffixTreeNode.cs:20`), leaf edge length includes the terminator (`SuffixTree.Construction.cs`, `LengthOf`: `_position + 1 - Start` for `BOUNDLESS`), the empty-suffix leaf hangs under the root with `Start = n`, `Traverse` visits children by ascending key so key `-1` comes first (`SuffixTree.Diagnostics.cs:189-191`, `:207`, line numbers at `b0922125`). Edge starts: leaves are created for increasing suffix start (Ukkonen processes suffixes in increasing order), a split keeps the old start (`SuffixTree.Construction.cs:41`) and the lower part advances it (`:47`), so by induction `Start - parentDepth` of every edge is the **minimum** suffix start in its subtree, i.e. `occ = min(SA[lb..rb])` (ADR-001's H-OCC). Experiment: the Traverse event streams (`VisitNode(start, end, leafCount, childCount, parentDepth)`, `EnterBranch` keys, `ExitBranch`) of the Ukkonen port and of the ESA model with `occ = min(SA[lb..rb])` are identical for all non-empty strings of the same sets as in item 2 (only `n = 0` differs, MIN-2); with `occ = SA[lb]` they differ for 2,035 of 2,047 binary strings, so the pre-pass is necessary. `NodeCount = 1 + I + (n + 1)`, `LeafCount = n`, `MaxDepth = n` follow from the same streams. Ukkonen == v6 is already pinned by tests (`tests/SuffixTree/SuffixTree.Persistent.Tests/Serialization/LogicalPersistenceTests.cs:20-41`, `Parity/B05SuffixTreePropertyParityTests.cs:153`), so the hash is a valid L3/L5 oracle for ESA once item 4 holds.
5. **What `Traverse` consumers need.** `DeepestInternalNodeCollector` slices at `end - length` (`SuffixTreeAlgorithms.cs:683-686,717-724`), `MaximalPairCollector` uses `p = start - depth` for leaves and skips `p >= n` (`Repeats.cs:131-134`), `ColorCountingCollector` the same (`KCommon.cs:255-256`); none needs the leftmost occurrence, a valid one suffices (ADR-001 section 4 is right), and all need every leaf to be followed by an `ExitBranch` (`_leafPending`).
6. **Memory arithmetic.** Core 1.0 + 4.0 + 1.0 + 4.0 + 0.4 = 10.4 B/char; Full 10.4 + 4.0 + 0.4 = 14.8 (MAJ-3 changes the 0.4); +`NEXTSYM` 15.8; worst cases 2 + 4 + 4 + 4 + 0.5 = 14.5 and 18.9. `BUCKET` for 10 Mbp DNA: k = 10 gives 4,194,304 B <= 5,000,000 B, k = 11 gives 16.8 MB (so k = 10, 4 MB = 0.4 B/char). Phase table: 8.3 / bound 9.1 / 12.0 / 16.4 (ADR says 16.5). The peak RSS plan holds with 1.5-4.5 B/char of headroom (corrected from "2-5"). Header arithmetic: 128 + 62 * 64 = 4096; section entry fields sum to 64; the magic as little-endian `int64` is `0x1A0A0D4153455389`. Limits: `Array.MaxLength = 2,147,483,591`; .NET string maximum 1,073,741,791; "valid because n + 1 < 2^31" for the sign-bit flag (R6) holds.
7. **v6 magic and dispatch.** `0x5452454558494646` decodes to `TREEXIFF` big-endian; the on-disk bytes are `46 46 49 58 45 45 52 54` (written by `FinalizePipeline.cs:83` via `WriteInt64`; mapped provider stores natively, heap provider uses `WriteInt64LittleEndian`). The v6 loader checks size >= 88, then the magic, and throws `InvalidOperationException("... Magic number mismatch.")` (`PersistentStorageHeaderValidation.cs:117-118`), so an ESA file is rejected by it as ADR-003 section 8 states. The two magics differ in every byte.
8. **Gate arithmetic.** 10 x 0.328 = 3.28 ~ 3.3 s. Count >= 450k and locate >= 250k against the best measured tools (747,415 and 1,140,278, `BENCHMARK.md:61-66`) give ratios 1.66 and 4.56, geometric mean 2.75 <= 3 (PLAN.md:84). `0.62` internal nodes per char follows from 16,229,747 nodes for 10 M leaves (`BENCHMARK.md:189`).
9. **libsais oracle.** The pinned commit `1aae6344` (v2.9.1) contains `include/libsais16.h` (uint16 text) and `libsais_plcp`/`libsais_lcp` (LCP), so the UNVERIFIED in row 1a.6 is resolved. SA order convention (shorter suffix first) equals our `SA[1..n]`.
10. **Process rules.** Managed only (BCL `MemoryMappedFile`, `NativeMemory`, `Sse42.Crc32`); no P/Invoke planned; the ESA reader does not copy the v6 `madvise` imports (`MappedFileStorageProvider.Prefetch.cs:73-76`); Ukkonen is untouched: the test adapter of 1b.0 can use only public members (`CountOccurrences`, `FindAllOccurrences`, `Text`, `Traverse`), so no `InternalsVisibleTo` edit of the Ukkonen or persistent projects is needed.
