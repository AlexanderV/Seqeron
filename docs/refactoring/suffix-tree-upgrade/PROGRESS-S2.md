**What the measurements say (details and spreads in ADR-005 and `analysis/s2/results`; every row reproduces from `analysis/s2/README.md`).**
* **Width of stored positions (O1).** 4 bytes is the fastest and covers n + 1 <= 2^32 - 1 (4.29 Gbp): the human genome (3.1 Gbp) needs no wider entry, and the builder writes 4-byte entries everywhere (no 40-bit path exists in the code: `SesaBuilder.cs:546`, `Dist.cs:256-268`; ADR-004's `w = 5` was never built). 5 bytes (40-bit): +6 to +13 % on the count descent and +25 % on locate (four threads), up to +31 % on a random read, not slower than 8 bytes and 37 % smaller: the width above 2^32 - 4, chosen once from n.
  The hybrid with escapes is **bigger** than 40-bit at 6.2x10^9 (5.79 against 5.00 B per entry), 1.26-1.28x slower on count and 2.9-3.6x on locate: rejected; a 34-bit line-packed form: 1.16-1.25x on count, 2.2-3.2x on locate: rejected. `long` registers over the same 4-byte entries: the `int` code takes 1.01-1.05 of their time (four threads; null experiment 0.95-1.03), so `long` is not slower.
* **The delta form of CHILD (the owner's own candidate) is the real lever.** 99.2-99.5 % of the child cells lie within 127 of their own index on random DNA, a genome-like text and a repeat text; a 2-byte cell (kind in two bits, 14-bit distance, 0.007 % escapes in a **hash table**: a binary search costs +26 to +46 %) is 1.007 / 1.016 / 1.007 of the 4-byte tagged cell at 10^8 (1.045 / 1.029 / 1.056 in the repeat on the pushed head; null 0.97-1.02) and 1.07 / 1.08 / 1.06 of it, 0.99 / 1.02 / 1.00 of the packed 4-byte cell, at 5x10^8, the only 4-byte cell above 2^30 symbols.
  CHILD 4 -> 2 B/char (Core 9.25 -> 7.25, Full 13.25 -> 11.25), independent of n. PSI increments are <= 255 in 99.92-100.000 % of the entries (access cost not measured).
* **2-bit text.** The container already has it (TEXT codec 4). Read cost against a byte: +34 % (b = 2) / +45 % (b = 3) per random symbol, +8 % per dependent read, -13 % per long common extension (26.7 against 30.8 ns). What S2 adds is the in-memory packed text without a string and a sigma = 4 kernel experiment under the stopping rule.
* **The gate rows on this machine** are nearly met by S1: 10^8 in 17.6 s, 13.25 B/char Full / 9.25 Core; **5x10^8 in 79.0 s (Core) and 104.7 s (Full); the libsais suffix array of the 5x10^8 text equals SA[1..n] of the container (SHA-256 `6edf12d4...`)**. The gate of S2 is therefore about reach (a reader and an API above 2^31, the ingest, the public builder, the pack from the container, `Structure` at scale, the hand-off), not speed.

**Limits** (said once). The closed forms cover three periodic families and `u^m`; there is no closed form of the child table of `u^m` (the engine's scan over the generated LCP is the oracle there) and none for a text that is not periodic. A sparse file proves the file and mapping arithmetic above 2^31 and 2^32 (offsets, `long` section lengths, `Header` and `Sections` at 26-78 GB); it cannot prove data, durability, a write path or the `Structure` level (its content is zero except for the ends). The `Sections` pass over holes measures the CRC and the page-fault rate of a hole, not the disk of a real container (the page cache holds zero pages). The 5-byte reader and format exist only as the test-side `Sesa5Image` until S2.7; the encoder cannot make a container above 4.29 Gbp (it re-encodes what a 4-byte container holds), so a real 5-byte container above 2^32 exists only as a shell. `SesaOracle.FromBytes` reads whole files: the width-5 round trips stop at 10^6 symbols. The mutation audit covers the test-support code only, as the brief says (the closed forms are oracles: a wrong oracle that agrees with a wrong engine is the risk it is meant to remove, by three independent comparisons).
