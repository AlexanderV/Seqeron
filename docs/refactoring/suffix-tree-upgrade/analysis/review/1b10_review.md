## 1. Verdict

**The engine is releasable; the package as it stands is not.** The in-memory ESA and the container reader are among the most carefully verified code of this repository (I compared only with what I read): the contract matches the Ukkonen tree on every member I tried, `Checked` mode held against 73,800 hostile containers, the reader protocol has a
proof that I could not break and 9,100 races that did not either, the builder survives `kill -9` at all 14 of its hook points and a full disk at all 14 (an `IOException`, never a signal), and every figure of the 1b.9 gate that I could reproduce reproduced. What stops a 1.x tag is not in the engine: (1) **R01**, a wrong
answer from `TryExtendRight(l, c, out l)`, the most natural loop over the long API, with no test and no warning in the documentation; (2) **R03**, there is no package: the metadata is the placeholder `Package Description`, the library drags `SuffixTree.Persistent` along, only `net10.0`; (3) **R02 and the internal builder**: two overlapping builds of one
target make the first report success and publish the second one's half-written file, and no program that references the library can build a container at all, although the format is frozen as SESA 1.0; (4) **R04**, the checked build, the Exhaustive and Fuzz categories, the Vectors and the harness are not in the CI, so the bounds checks that make `Checked` credible are
never exercised by it (the default run skips the tests that need the checked accessor). Everything else is Minor or documentation. My own recommendation for the order is in section 7.

### 3.1 R01: the aliased locus

Program (a scratch console project referencing `SuffixTree.Esa`; the text is `abracadabra`):

```csharp

foreach (char c in "abr") { bool ok = tree.TryExtendRight(a, c, out a); /* print ok, a */ }
```

Output: `[a: True [1..5] depth 1 aux 1] [b: False [0..0] depth 0 aux 0] [r: ArgumentException]`. The same loop with a new variable per step gives `[2..3] depth 3 aux 4`, count 2. The span overload: `tree.TryExtendRight(s2, "a".AsSpan(), out s2)` with `s2` = the locus of `abr` returns `True [2..3] depth 1 aux 4` (expected depth 4).
`tree.TryExtendLeft(e, 'a', out e)` throws `ArgumentException: [0..0] depth 0 aux 0 is not a locus of this index`. Through `ISuffixIndex` the same. `TryParent`, `TryChild`, `TrySuffixLink`, `GetChildren(kids[1], kids)` give the same answers aliased or not. **The test that would fail today** (NUnit, for `IndexConformanceTests` or the facade tests):

### 3.2 R02: two builds of one target

Scenario (internal builder called by reflection with the hook option; text of 10^6 symbols, `Resume` off): build A sleeps 4 s at the hook `checksummed` (its container is complete and checksummed, the header is not written); 1.2 s after A started, build B starts on the same target and sleeps at `packed` (it has deleted A's temporary
file and created its own, zero-filled and reserved). Result: `A: BUILT out.sesa size=13267521 in 4.53s` (exit 0), `B: FileNotFoundException: Could not find file 'out.sesa.tmp'`, the target exists with the right size; its SHA-256 differs from the reference build; `Open` at `Header` succeeds, the first query throws `InvalidDataException: the child table or the LCP array is inconsistent ... the file is damaged`,
`Sections` and `Structure` refuse it (`section SA has CRC-32C 024D5F2A but the section table says 12149AE6`). Without the hooks, ten pairs with delays of 0.60-1.15 s between two builds of 4 M symbols: 7 pairs both failed (`DirectoryNotFoundException` / `FileNotFoundException`, nothing published), 2 pairs both built the same file, 1 pair A failed and B published the reference.

### 3.6 What held (the black-box runs of the builder and the reader)

* **`kill -9` at every hook point of the build**, 1.2 M symbols, 14 points x {`Resume` off, on} = 28 kills: the target was never present (no earlier target) and the second call of the same build produced a container whose SHA-256 equals the clean build's, in all 28; left behind after a kill: `<target>.tmp`, `<target>.tmp.d` (and `<target>.lock` with `Resume`); an existing good target stays as it was both after a failed build (missing input: `DirectoryNotFoundException`) and after a kill.
* **Resume after damage** (kill at `lcp-child-built` with `Resume` on, then damage the kept files, then resume): a flipped byte in the middle of SA, in the first SA entries, in the child table, in the LCP array, in the header page, in the zero padding after the text; `state.json` deleted; `state.json` garbage; the temporary container truncated to 1 MB: **9 of 9 resumes give a container whose SHA-256 equals the clean build's** (the 1b.9e.1 property holds).
* **The disk fills at every hook point** (a 48 MB tmpfs, 1.2 M symbols: the pre-flight passes at 30 MB), 14 points: `IOException` ("not enough free space ..." before the container is created, "No space left on device" on a scratch file, "Failed to create ... because the disk was full") in 6 points, success in the 8 where no new block was needed; **never a signal**, nothing left behind in any case. The pre-flight alone: a 4 M text on the same disk -> `IOException: not enough free space ... 101020929 bytes ... 50331648 bytes are available`.
* **A read-only file system** (the tmpfs remounted `ro`): `IOException: Read-only file system : '.../out.sesa.tmp.d'`, nothing left. **A directory that does not exist**: `DirectoryNotFoundException`. **A relative target, a path with spaces and non-ASCII letters** for both the input and the target: built and opened.
* **The input changed between the two passes** (a byte appended, a byte replaced): `InvalidOperationException` ("the input has 1000001 bytes, 1000000 were scanned ..."; "symbol 0 occurred 250426 times in the second pass and 250427 times in the first"), no target.
* **A file truncated while a tree reads it** (the container cut to 8 KiB under a running reader): `Fatal error. System.AccessViolationException` in `Checked` and in `Trusted` (the documented property of a mapping, ADR-004 "1b.7f" limit d).
* **Reader races** (section 0, item 5) and **hostile containers** (item 4): clean.
* **Open of the 10 Mbp container, fresh processes** (page cache warm): `Header` 12.2-14.2 ms (5 processes; the committed row is 13.1-15.4 ms), `Sections` 41.6 ms, `Structure` 1.41 s (committed: 33.0 ms and 1.50 s); the first query 4.5 ms.
* **Memory** (GC heap delta around `CreateEsa`, a 10 Mbp text): +95.4 MB = **10.00 B/char** on top of the caller's string (2 B/char, shared, not copied), +39.4 MB = 4.13 B/char for the navigation pack (14.13 in all), all of it returned after the tree is dropped and a collection runs; `a^n` and `abab...` at 5 Mbp: 13.00 B/char.

## 6. Tests and CI

* **Are the tests meaningful?** Yes, with one structural caution. The oracles are independent of the code under test wherever it matters: brute force from the definitions (`IndexContractOracle`), the Ukkonen and v6 trees, the libsais hashes of 632 vector sets, the independent `SesaOracle` decoder with distinct field values, the independent `e8-verify`. The one limit the ADR names (the container oracles were written by the same
  implementer from ADR-003) is real but mitigated by the SHA-256 equality with the extraction script and by my own fuzz. The corruption lane is stronger than I expected: sealed damage, header fields with the CRC recomputed, and a guard-page image; my 73,800 independent mutants found nothing it had missed.
* **Gaps.** No aliasing test (R01); no test of a caller error on a container-backed text (R06); no test of two overlapping builds (R02); no architecture test (R16); the memory-safety net of `Checked` is skipped in the default run (R04).
* **Categories and what a CI job should run** (Release, this machine, idle, one set at a time): default 14 min 31 s (in CI today via the solution); checked build 13 min 35 s (+ about 1.5 min compile), Exhaustive 17 min, Fuzz 14 min 48 s, Vectors 1 min 2 s, the harness 10-minute budget 12-15 min (719 s wall in the committed run, 912 s in mine). **A job that runs them all costs about 60-65 minutes on this 4-vCPU machine** (checked 15 + Exhaustive 17 + Fuzz 15 + Vectors 1 + harness 12-15; the sets are mostly single-threaded, so a 2-vCPU runner is slower by less than 2x). On a change under `src/SuffixTree/**` the checked build alone (about 15 minutes) is the best trade; the rest nightly.
* **Flaky or timing-sensitive tests.** The known one (the 1b.3 allocation test) was fixed in 1b.9h (a no-GC region); I saw no failure in my default run. Tests with `Thread.Sleep` / `Stopwatch` (82 uses) are limited to the explicit cost drivers and watchdogs. 37 skipped tests in the default run are by design.
* **Tests that cannot fail:** the two `Assert.Pass()` cost drivers (explicit, R13); `Assert.Pass("no expectation set")` when `ESA_EXPECT_BOUNDS` is unset (`BufAndArenaTests:21`): that is the check that the CI would need to set.
