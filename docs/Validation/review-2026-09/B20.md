## Confirmed fixes

### F1 — PARSE-FASTA-001: `ToFasta`/`WriteFile` with `lineWidth: 0` loops forever
- Repro: `FastaParser.ToFasta(entries, 0)` never returns (wrap step 0); negative width threw an unrelated AsSpan error.
- Source: Biopython `FastaWriter` ("Use zero (or None) for no line wrapping"). Reference: Biopython `wrap=0` → `">s1 demo\nACGTACGTAC\n"`; `wrap=-1` → ValueError.
- Fix: 0 = unwrapped; negative → `ArgumentOutOfRangeException`. Tests `ToFasta_LineWidthZero_WritesUnwrappedSequence`, `ToFasta_NegativeLineWidth_ThrowsArgumentOutOfRange`.

### F2 — PARSE-FASTA-001: `;` comment lines parsed as sequence (threw ArgumentException)
- Repro: `">s1\n;c\nACGT"`.
- Source: Pearson fasta36 `nmgetlib.c` `agetlib` skips `;` lines; Biopython `fasta-pearson`. Reference: `">s1 desc\n;comment line\nACGT\n;another\nGGCC\n>s2\n;c\nTTAA\n"` → [(s1, ACGTGGCC), (s2, TTAA)]; leading `;` lines before first `>` ignored.
- Fix: `;` lines ignored on all parse paths (sync/async/alphabet). Tests `Parse_SemicolonCommentLines_AreIgnored`, `Parse_LeadingSemicolonComments_AreIgnored`, `ParseFileAsync_And_AlphabetOverload_IgnoreCommentLines`.

### F3 — PARSE-FASTA-001: id split only on space/tab
- Source/reference: Biopython `title.split(None,1)[0]`: `>s1\x0bdesc` → `s1`, `>s1\xa0desc x` → `s1` (Seqeron returned whole title).
- Fix: split at first `char.IsWhiteSpace`. Test `Parse_HeaderSplitOnAnyWhitespace_MatchesBiopythonId`.

### F4 — PARSE-FASTA-001: no writer for `FastaRecord` (RNA/protein/IUPAC)
- Added overloads `ToFasta(IEnumerable<FastaRecord>, int)`, `WriteFile(string, IEnumerable<FastaRecord>, int)` (additive). Reference: Biopython wrap=4 on `mwyx/BZJUO*` → `>p1 prot\nMWYX\nBZJU\nO*\n`. Tests `ToFasta_FastaRecords_Protein_WrapsLikeBiopython`, `WriteFile_FastaRecords_WritesToFastaOutput`.


### F5 — PARSE-FASTQ-001: Auto encoding detected per record and order-dependent
- Defect: `Parse(…, Auto)` called `DetectEncoding` separately for each record. The detector also returned Phred+64 at the first char > 'I' (73), before looking at the rest of the string. Repro 1: in a Phred+64 file `@r1/hhhh`, `@r2/BBBB` (an Illumina 1.5 'B' tail read), r2 decoded to [33,33,33,33]. Repro 2: `@r1/JJJJ`, `@r2/!!!!` gave r1 = [10,10,10,10]. Repro 3: quality `J5` gave Phred+64 → [10,0].
- Source: FastQC `PhredEncoding.getFastQEncodingOffset` + `PerBaseQualityScores.calculateOffsets` decide the offset from the lowest character over the whole file. Cock et al. 2010 ranges: 'J' = Q41 is the Illumina 1.8+ ceiling.
- Reference: Biopython `fastq-illumina` r2 = [2,2,2,2]; Biopython `fastq` r1 = [41,41,41,41]; `J5` → [41,20].
- Fix: Auto mode now detects the encoding once per input with the canonical `QualityScoreAnalyzer.DetectEncoding(IEnumerable<string>)`. `ParseFile` and `Parse(string)` make two streaming passes; `Parse(TextReader)` buffers the records. `FastqParser.DetectEncoding(string)` delegates to `QualityScoreAnalyzer.DetectEncoding(string)`.
- Tests: Parse_Auto_Phred64FileWithIllumina15BRead_DetectedFileLevel, Parse_Auto_Phred33FileWithQ41Read_DetectedFileLevel, Parse_Auto_TextReaderAndFile_UseFileLevelEncoding, DetectEncoding_LowCharAfterHighChar_IsPhred33, DetectEncoding_AtThenAboveJ_IsPhred64, DetectEncoding_AtThenJ_IsAmbiguousDefaultsPhred33.

### F6 — PARSE-FASTQ-001: malformed records were assembled instead of rejected (INV-01 violated)
- Defect: `@rec/ACGTACGT/+/II` produced a record with 8 bases and 2 scores; a later `TrimByQuality` call then threw IndexOutOfRange. A quality line longer than the sequence was accepted. A missing '+' pulled the quality line into the sequence. A header without '@' was silently dropped. A '+' caption that differed from the title, and whitespace inside the sequence, were both accepted.
- Source: the Sanger FASTQ definition (Cock et al. 2010), as implemented in Biopython 1.88 `FastqGeneralIterator`.
- Reference (Biopython ValueError for each): "Lengths … differs for rec (8 and 2)", "(4 and 12)", "End of file without quality information.", "should start with '@'", "captions differ", "Whitespace is not allowed", "Unexpected end of file". Biopython's `tricky.fastq` example parses to 4 records, and record 4's quality is `IIIIIII.IIIIII1@44@-7.%<&+/$/%4(++(%`.
- Fix: new private `ReadRawRecords`, a port of `FastqGeneralIterator`. It throws `FormatException` on every case above. Blank lines between records are still allowed, and quality is still read by length.
- Tests: Parse_BiopythonTrickyExample_ParsedByQualityLength, Parse_PlusCaptionDiffers_ThrowsFormatException, Parse_WhitespaceInSequence_ThrowsFormatException, Parse_QualityLengthMismatch_ThrowsFormatException, Parse_ZeroLengthRecordAndBlankSeparators_Accepted. The FASTQ fuzz section was rewritten: ParseFastq_*_RejectedWithFormatException, ParseFastq_TruncatedRecords_RejectedNeverIndexOutOfRange, ParseFileFastq_FinalRecordTruncated_FirstRecordYieldedThenFormatException, ParseFastq_RandomByteBody_FormatExceptionNoHang, ParseFastq_PureRandomBytesNoHeader_FormatExceptionNoHang.

### F7 — PARSE-FASTQ-001: quality symbols outside the encoding range were silently clamped to Q0
- Defect: `DecodeQualityScores("J5hh", Phred64)` returned [10,0,40,40]. An explicit Phred+64 parse of Phred+33 data therefore produced corrupted scores without any error.
- Source/Reference: Biopython `fastq-illumina` raises InvalidCharError on "J5hh"; `@h~~` → [0,40,62,62].
- Fix: `DecodeQualityScores` now delegates to the canonical `QualityScoreAnalyzer.ParseQualityString`, which throws ArgumentOutOfRangeException. `Parse` rethrows this as FormatException.
- Tests: DecodeQualityScores_CharOutsideEncodingRange_Throws, ParseFastq_ControlCharQuality_RejectedWithFormatException.

### F8 — PARSE-FASTQ-001: ErrorProbabilityToPhred was not monotone and accepted invalid probabilities
- Defect: p = 1e-10 → 100 while p = 0 → 93, so a smaller error probability gave a lower score. p = 1.5 → −2; p = NaN → garbage.
- Source: Phred+33 can represent at most Q93 (ASCII 126 − 33; Cock et al. 2010). Biopython truncates written Sanger qualities at 93. A probability must lie in [0,1].
- Reference: −10·log10(1e-10) = 100 → capped at 93; 1e-9 → 90; 0.5 → 3.
- Fix: every result is capped at Q93, and NaN or p outside [0,1] throws ArgumentOutOfRangeException. The MCP wrapper already rejected values outside [0,1].
- Tests: ErrorProbabilityToPhred_TinyProbability_CappedAtQ93_Monotone, ErrorProbabilityToPhred_OutsideProbabilityDomain_Throws (3 cases), ErrorProbabilityToPhred_Zero_ReturnsMaxQuality.

### F9 — PARSE-FASTQ-001: TrimAdapter differed from cutadapt's 3' adapter semantics
- Defect: a full adapter at position 0 was never trimmed (`adapterPos > 0`). A 3' partial match also won over an earlier full occurrence: for `ACGTACGTAGATCGGAAGAGCTTTTTAGATC` the result was `…AGCTTTTT` instead of `ACGTACGT`.
- Source/Reference: cutadapt 5.2 `-a AGATCGGAAGAGC -e 0 -O 5` gives: `AGATCGGAAGAGCACACGTC`→"", `ACGTACGTAGATCGGAAGAGCTTTTTAGATC`→`ACGTACGT`, two full occurrences→leftmost `CCCC`, `…AAAAGATCG`→`ACGTACGTACGTAAA`, a 4-base partial stays unchanged, and `AGATCGGAAG`→"".
- Fix: cut at the leftmost i where read[i..] matches an adapter prefix of length min(|A|, L−i) ≥ minOverlap (case-insensitive). Matching is exact only; this is documented.
- Tests: TrimAdapter_MatchesCutadapt (7 cases).

### F10 — PARSE-FASTQ-001: WriteToFile wrote a UTF-8 BOM
- Defect: `new StreamWriter(path, false, Encoding.UTF8)` writes the bytes EF BB BF before '@'.
- Reference: on such a file Biopython `FastqGeneralIterator` raises "Records in Fastq files should start with '@' character", and cutadapt 5.2 fails with "Input file format not recognized … b'\xef\xbb\xbf@'".
- Fix: the writer now uses `new UTF8Encoding(false)`.
- Test: WriteToFile_NoByteOrderMark_FirstByteIsAt.

### F11 — PARSE-FASTQ-001: record id was split on space only
- Defect: for `@r1\tdesc here` the id was `r1\tdesc here`; for `@ odd` the id was " odd".
- Reference: Biopython SeqIO `fastq` gives id `r1` and id `odd` (`title.split(None, 1)[0]`).
- Fix: shared `SequenceFormatHelper.SplitTitle`, applied to the trimmed title.
- Tests: Parse_TabInTitle_SplitsIdOnAnyWhitespace, Parse_HeaderWithLeadingSpace_IdIsFirstWord.

## Duplication removed

- PARSE-FASTA-001: 4 copies of the FASTA line-reading loop (sync/async × FastaEntry/FastaRecord) collapsed into one private `RecordAccumulator` + `ReadRawRecords`/`ReadRawRecordsAsync`; writers share `AppendRecord`. MCP `fasta_parse`/`fasta_format`/`fasta_write` delegate.

- `FastqParser.DetectEncoding`, `DecodeQualityScores`, `EncodeQualityScores` (clamp, then `ToQualityString`) and `PhredToErrorProbability` now delegate to the canonical `QualityScoreAnalyzer` methods. Auto mode uses `QualityScoreAnalyzer.DetectEncoding(IEnumerable<string>)`.
- The id/description split that FASTA and FASTQ each had is now one internal helper, `SequenceFormatHelper.SplitTitle`. `FastaParser.SplitHeader` was removed and its callers use the helper.
- `FastqParser.TrimByQuality` and `QualityScoreAnalyzer.QualityTrim` now share the new internal `QualityScoreAnalyzer.FindQualityTrimBounds` (additive). QualityTrim output is unchanged and its tests are green.
- Flagged for the QUALITY-PHRED-001/QUALITY-STATS-001 reviewer, not fixed here because it changes that unit's contract:
  - `QualityScoreAnalyzer.ParseFastq`/`ToFastq` are a second, naive 4-line FASTQ parser and writer. It has no multi-line support and no validation, and the '+' line is not checked. It should delegate to FastqParser's reader.
  - `QualityScoreAnalyzer.ErrorProbabilityToPhred` returns 60 for p ≤ 0, an unsourced "max practical" value, while FastqParser returns 93. It has no cap for tiny p (1e-10 → 100) and no domain check.
  - `CharToPhred`/`QualityStringToPhred` duplicate `ParseQualityString` without its range check.
  - The two `QualityEncoding` enums and the two `FastqRecord` types are public-API duplicates, which cannot be merged without a breaking change.

## Simplifications kept (with reason) / LIMITATIONS proposals

- PARSE-FASTA-001 (LIMITATIONS proposal): header-only FASTA records (defline with no sequence) are not yielded (Biopython yields empty-sequence records); `;` lines are always comments — legacy Pearson/PIR use of a leading `;` line as title is not supported; sequences are uppercased on parse (Biopython preserves case); default `Parse` path is strict A/C/G/T (use `SequenceAlphabet` overloads for IUPAC/RNA/protein).

- PARSE-FASTQ-001 (existing entry; the wording is now accurate for the main parser): "`FastqParser.Parse`/`ParseFile` in Auto mode detect the Phred offset once per file with `QualityScoreAnalyzer.DetectEncoding(IEnumerable<string>)`. Only a file in which every quality character lies in ASCII 64–74 remains ambiguous; it defaults to Phred+33 under Permissive and throws otherwise."
- New simplification note (doc only, no catalog entry needed): "`FastqParser.TrimAdapter` implements cutadapt's regular 3' adapter removal with exact matching only (`-e 0`). cutadapt's default error-tolerant (10 %) alignment is not modelled."
- New simplification note: "`FastqParser.Parse(TextReader, Auto)` buffers that reader's records to determine the file-level encoding, because a TextReader cannot be rewound. Use `ParseFile`, `Parse(string)` or an explicit encoding for streaming."
