## Confirmed fixes

### F1 — CRISPR-PAM-001: reverse-strand `PamSite.TargetStart` was not a genome coordinate
- **Defect:** for reverse-strand hits `TargetStart` indexed into the reverse-complement string while `Position` was a forward-strand coordinate, so the two fields lived in different frames. Repro: `FindPamSites("CCAACGTACGTACGTACGTACGTACGTACGT", SpCas9)` → `TargetStart` 8; CRISPOR `flankSeqIter` gives guideStart 3. It leaked into `DesignGuideRnas` (`GuideRnaCandidate.Position = pamSite.TargetStart`), so reverse-strand guides carried a meaningless position.
- **Source opened:** CRISPOR `crispor.py` (master, raw.githubusercontent.com): `findPat` L951, `patMatch` L2347, `findPams` L1033 (incl. doctests), `flankSeqIter` L1582, `findAllPams` L4627, `setupPamInfo` L458, Cpf1 staggered-cut text L1565.
- **Cross-check:** CRISPOR's `revComp/patMatch/findPat/findPams/flankSeqIter` copied verbatim into Python and driven directly against a C# dumper: 4 designed + 60 pseudo-random sequences (seed 20260928, len 10–200) × 7 systems = 136 reference sites. Before: all forward sites matched, all reverse sites mismatched; after: 0 mismatches.
- **Fix:** in `FindPamSitesCore` reverse branch, `TargetStart = Position + pamLen` (PAM-after) / `Position - guideLength` (PAM-before) — CRISPOR's minus-strand `guideStart`. Forward-strand output byte-identical.
- **Tests:** `FindPamSites_SpCas9_ReverseStrand_MatchesCrisporConvention`, `FindPamSites_Cas12a_ReverseStrand_MatchesCrisporConvention`, `FindPamSites_AllSites_AreConsistentInForwardCoordinates` (4 parametric), updated `FindPamSites_SpCas9_SearchesReverseStrand`.

### F2 — CRISPR-PAM-001: reverse-strand `PamSequence` was reported reverse-complemented
- **Defect:** reverse SpCas9 hits reported `CCA` and Cas12a `TAAA` — strings that do not satisfy the system's own PAM motif — while `TargetSequence` was correctly protospacer-oriented (violating documented INV-01).
- **Source / cross-check:** same CRISPOR run above (`pamSeq`).
- **Fix:** report the matched window as read on the protospacer strand (`TGG`, `TTTA`).
- **Tests:** same reference-row tests as F1 (they assert pamStart/guideStart/pamSeq/guideSeq jointly).


### F3 — CRISPR-GUIDE-001: cut site was wrong on the reverse strand and not exposed
- **Defect:** `IsInRegion` computed the cleavage position from `pamSite.Position` with the forward-strand formula for *both* strands (`Position - 3` for Cas9, `Position + pamLen + 18` for Cas12a), so on the minus strand it pointed 3 bp on the wrong side of the PAM and region filtering admitted/rejected the wrong guides. The convention was also private, so callers could not reproduce the region test.
- **Source opened:** CRISPOR `crispor.py` (master, raw.githubusercontent.com): the expected cleavage position "-3bp 5' of the PAM site", the `startFt = start - 3` / `ftSeq + "---"` cut-marker construction, and the Cpf1 staggered-cut text ("after the 18th base on the non-targeted strand which has the TTTV PAM motif", Zetsche et al. 2015, Cell 163:759, Fig. 3).
- **Fix:** new public `CrisprDesigner.GetCutSite(PamSite)` returning a forward-strand 0-based coordinate for both strands (Cas9: `Position - 3` / `Position + pamLen + 2`; Cas12a: `Position + pamLen + 18` / `Position - 19`); `IsInRegion` delegates to it and no longer takes a system.
- **Tests:** cut-site tests for both strands and both PAM topologies; region-boundary tests for `DesignGuideRnas`.

### F4 — CRISPR-GUIDE-001: the site's CRISPR system was silently replaced by SpCas9
- **Defect:** `EvaluateGuideRna(PamSite, …)` mapped `system.Name` back to a `CrisprSystemType` with a `_ => CrisprSystemType.SpCas9` fallback, so SpCas9-NAG, AsCas12a, LbCas12a and CasX guides were re-evaluated as SpCas9 — wrong seed-region orientation (PAM-before systems take the 5' end) and wrong reported system/guide length.
- **Fix:** the pipeline passes `pamSite.System` straight into the shared `EvaluateGuideRnaCore`; no name-based remap exists any more.
- **Tests:** per-system evaluation tests asserting the reported system and the seed window orientation for a PAM-before system.

### F5 — CRISPR-GUIDE-001: designed guides carried no published on-target score, and output was unranked
- **Defect:** `DesignGuideRnas` returned candidates in PAM-scan order scored only by the library's composition heuristic, although the validated Doench 2016 Rule Set 2 / Azimuth model was already implemented (`CalculateOnTargetRuleSet2`) — it was simply never applied to designed guides, because nothing extracted the model's 30-nt context. The XML doc also claimed a "ranked list".
- **Source opened:** CRISPOR `crispor.py` / `crisporEffScores.py`: the 30-mer context window (`trimSeqs(seqs, -24, 6)` around the PAM start = 4 nt 5' flank + 20-nt protospacer + 3-nt PAM + 3 nt 3' flank), the per-guide "Doench '16" efficiency column, and `mergeGuideInfo`'s `guideData.sort(reverse=True, …)` ranking.
- **Fix:** `TryGetRuleSet2Context` builds that window on the protospacer strand for 20-nt NGG systems (null when the system does not qualify, the flanks do not fit, or the window is not all A/C/G/T — the reference's "can't do Ns"); new `GuideRnaCandidate.Context30Mer` / `OnTargetScore`; new `GuideRnaRanking` (`Score` default, `OnTargetRuleSet2`) with a deterministic position/strand tie-break.
- **Tests:** context extraction on both strands (incl. flank-overrun and N cases), score plumbing, ranking order and tie-break determinism.

### F6 — CRISPR-GUIDE-001: self-complementarity used an unsourced ad-hoc metric only
- **Defect:** the only self-complementarity measure was a normalised complementary-pair fraction with an unsourced 0.3 threshold and an `L²` denominator; the published measure used by the reference tool (count of 4-bp stems, guide-internal or against the sgRNA scaffold) was absent, as was any way to filter on it.
- **Source opened:** CHOPCHOP `chopchop.py` (Carl-labhub/chopchop-clone mirror of the Bitbucket repo — the Bitbucket raw endpoint and the valenlab GitHub paths 404): `STEM_LEN = 4`, `selfComp` / `calcSelfComplementarity` (`rvs[0:(L-i)]` with `L = len − STEM_LEN − 1`, `gccontent(stem) >= 0.5`, PAM excluded), `args.backbone = [revcomp(el) for el in split(",")]` with CLI help "same strand as guide", and `-filterSelfCompMax` default `-1` (no filter). Labun et al., Nucleic Acids Res 44:W272 (2016) / 47:W171 (2019).
- **Cross-check:** the reference algorithm was re-implemented verbatim in Python and driven against the C# method: guide `ACGGACTAGCCTACGTACGT` → 0 internal stems, 8 against the standard backbone `AGGCTAGTCCGT`, 1 when the backbone is passed already reverse-complemented (the palindromic-in-context window `CTAG` matches in both orientations); guide `ACGTACGTACGTACGTACGT` → 10. All identical in C#.
- **Fix:** new public `CountSelfComplementaryStems(guide, stemLength = 4, backboneRegions = null)` + `StandardSgRnaBackboneRegion`; reported on every candidate as `SelfComplementaryStems`; `GuideRnaParameters.MaxSelfComplementaryStems` (null = the reference's own no-filter default) filters in `DesignGuideRnas` and raises an issue in `EvaluateGuideRna` without deducting; the legacy `SelfComplementarityScore` is kept for backward compatibility and documented as the older metric.
- **Tests:** reference-locked counts above, inclusive-limit filtering, backbone orientation, argument validation.

### F7 — CRISPR-GUIDE-001: Graf 2019 inefficiency motifs were not reported
- **Source opened:** CRISPOR `crisporEffScores.py` `getGrafType` (TT-motif: ends `TTC`/`TTT`, or last 4 bases are only T/C with ≥2 T, or contain `TT` with ≥3 T or ≥1 C; GCC-motif: ends `[AGT]GCC` or `GCCT`), applied by the reference to NGG systems only; Graf et al. 2019, Cell Reports 26:1098–1103.
- **Fix:** public `GetGrafMotif` + `GuideRnaCandidate.GrafMotif`, reported as an issue for NGG systems with no score deduction (CRISPOR reports it as a warning).
- **Tests:** each published motif branch and the NGG-only restriction.

### F8 — CRISPR-GUIDE-001: `AvoidPolyT` / `CheckSelfComplementarity` were ignored
- **Defect:** both `GuideRnaParameters` flags existed and were documented, but `EvaluateGuideRna` applied the TTTT (−20) and self-complementarity (−30 × score) penalties unconditionally, so switching them off changed nothing.
- **Fix:** both penalties are now gated on their flag.
- **Tests:** penalty on/off for each flag, asserting score and issue list.

### F9 — CRISPR-OFF-001: the MIT aggregate silently returned a perfect 100 for every non-20-nt system
- **Defect:** `CalculateMitSpecificityScore(string, DnaSequence, int, CrisprSystemType)` filtered its hits with `.Where(ot => ot.Sequence.Length == 20 && guide.Length == 20)`. For every system whose guide is not 20 nt — SaCas9 (21), Cas12a/AsCas12a (23), LbCas12a (24) — ALL hits were dropped and the empty-set aggregate returned **100**, i.e. a guide with real off-targets was reported as perfectly specific. A false 100 on a specificity score is the unsafe direction.
- **Minimal repro (before):** `CalculateMitSpecificityScore("ACGTACGTACGTACGTACGTA", new DnaSequence("ACGTACGTACGTACGTACGTCAAGAAT"), 3, CrisprSystemType.SaCas9)` → `100.0`, although `FindOffTargets` on the same input returns one real off-target (`ACGTACGTACGTACGTACGTC`, 1 mismatch). After: `95.91285612347565`.
- **Source opened:** CRISPOR `crispor.py` (master, `raw.githubusercontent.com`, 375 382 B): `calcHitScore` length handling **L2047-2067** (`>20` → last 20 nt, "S. aureus requires 21bp long guides. We fudge by using only last 20bp"; `==19` → `"A"`-pad, "first pos has no weight anyways"; `<19` → "I'm not sure if this score makes sense anymore"); the same 19-nt pad in `annotateOfftargets` **L1934-1936**; `hitScoreM` **L2045**; `calcMitGuideScore` **L2098-2104**; `pamIsCpf1` **L889-891**; `pamIsCasX` **L897-899**; Cpf1 zeroing **L1939-1942** and sentinels **L1986-1988**.
- **Cross-check:** `calcHitScore` transcribed verbatim into Python (throwaway scratchpad script, not checked in; it is a literal copy of crispor.py L2047-2109) and run independently: 21-nt pairs → `100.0` (identical), `100.0` (mismatch at index 0, outside the last-20 window), `41.7` (index 20), `6.389516129032259` (two mismatches). `calcMitGuideScore` unrounded: Σ=0 → `100.0`; Σ=12.5 → `88.88888888888889`; Σ=60.5 → `62.30529595015576`.
- **Fix:** new `CalculateMitHitScoreFudged` applying the reference's own length handling, plus `EnsureMitModelApplies`, which **throws** for PAM-before-target systems (the reference scores none of them: `mitScore = cfdScore = 0.0`, `guideScore = guideCfdScore = -1`). Refusing is the honest translation of those sentinels; returning `-1` would break the documented `[0, 100]` range and returning `100` is the defect. The `<19` branch is not implemented and documented as unreachable (every `GuideLength` ≥ 20 and `FindOffTargets` rejects a mismatched guide). **F14 supersedes the fudge for SaCas9.**
- **Tests:** `CalculateMitSpecificityScore_SaCas9_21ntGuide_RealOffTarget_IsNot100`, `…_TwoMismatches_MatchesReference`, `…_MismatchAtFivePrimeEnd_ScoredAsPerfectHit`, `CalculateMitSpecificityScore_Cas12aClass_WithRealOffTargets_Throws` (asserts the off-targets ARE there before asserting the throw), `CalculateMitSpecificityScore_PamBeforeTargetSystems_AlwaysThrow` (4 cases).

### F10 — CRISPR-OFF-001: the CFD genome aggregate never validated `maxMismatches`
- **Defect:** `CalculateCfdSpecificityScore(string, DnaSequence, int, CrisprSystemType, CfdAggregation)` cannot call `FindOffTargets` (it needs each hit's PAM, so it drives the private `FindOffTargetsWithPamCore` directly) and therefore skipped `FindOffTargets`' own `0 ≤ maxMismatches ≤ 5` guard entirely. Same F9 failure mode: a **negative** cap matches nothing, so the aggregate returned a perfect **100**.
- **Minimal repro (before):** `CalculateCfdSpecificityScore("GACGCATAAAGATGAGACGC", new DnaSequence("CTTGCGTCTCATCTTTATGCGTA"), -1, CrisprSystemType.SpCas9_NAG)` → `100.0` instead of throwing; `… , 99, …` scanned with no cap at all. The sibling MIT overload threw correctly for both, so the two aggregates disagreed on their own contract.
- **Source opened:** same `crispor.py` read; `maxMMs` bounds the `annotateOfftargets` edit-distance loop (**L1897**), and this library's documented bound is `FindOffTargets`' own `0..5` (TestSpec M-003).
- **Fix:** the overload now repeats `FindOffTargets`' guards in the same order and with the same exception types (guide null/empty → `ArgumentNullException`, genome null → `ArgumentNullException`, `maxMismatches` → `ArgumentOutOfRangeException`) before any system-specific check; the repetition is commented with why delegation is impossible.
- **Tests:** `CfdSpecificity_Genome_MaxMismatchesOutOfRange_ThrowsArgumentOutOfRange` (`-1`, `6`, `99`; asserts both genome aggregates), `CfdSpecificity_Genome_InvalidArguments_Throw`.

### F11 — CRISPR-OFF-001: `CfdAggregation.ParkinsonNormalized` was documented with a factor-100 error
- **Defect (documentation):** the implementation correctly computes `100 / Σ raw CFD`, but the enum member's XML summary stated the formula as `100 × 100 / Σ CFD` and the `ArgumentOutOfRangeException` message repeated it as "(100 x 100 / sum)". Over the raw CFD values this API takes, that is wrong by a factor of 100 — exactly the mistake the implementation had already been corrected for. A reader auditing the code against its own doc would have "fixed" the code back to the bug.
- **Source opened:** `crispor.py` `calcCfdGuideScore` **L2106-2109** (`100. * 100.0 / hitSum`) together with `calcCfdScore`'s `doCfdFix` rescaling **L2181-2182** (`cfd_score = cfd_score * 100.0`) and the flag's definition **L340** / **L7045-7047**. Both changes are gated on the *same* flag, so over raw inputs `100 × 100 / (100 × Σ raw) = 100 / Σ raw`.
- **Cross-check:** raw `{0.5, 0.25}` → `MitStyle 99.25558312655087`, `ParkinsonNormalized 133.33333333333334`; raw `{1.0}` → `99.00990099009901` / `100.0` (independent Python).
- **Fix:** enum summary and exception message restated in terms of the raw input, both naming the cancellation explicitly so the factor-100 trap is documented rather than just avoided.
- **Tests:** `CfdSpecificity_ParkinsonNormalized_TwoHits_MatchesReference`, `CfdSpecificity_SingleUnitHit_BothAggregationsMatchReference`, `CfdSpecificity_ParkinsonNormalized_ZeroSum_ThrowsArgumentOutOfRange`.

### F12 — CRISPR-OFF-001: `CalculateSpecificityScore` presented an unsourced heuristic as *the* specificity score
- **Defect:** the method's entire XML doc was "Calculates specificity score for a guide RNA (higher = more specific)", and the `crispr_specificity_score` MCP tool described it as "a single specificity score in 0..100" with no hint that `100 − Σ(5 per seed mismatch + 2 per distal mismatch)` is this library's own invention. Hsu 2013 motivates only the *direction* of the seed weighting; no source was found for the weights `5`/`2`, the 12-nt seed width, the linear sum or the subtraction from 100. Meanwhile the published MIT and CFD aggregates sat in the same class with **no MCP exposure at all**, so an MCP caller had no way to reach a sourced number.
- **Fix (campaign rule for unsourced convenience metrics — sourced or honestly declared *and* the published alternative offered):** XML doc now states plainly that it is this library's own heuristic, lists its consequences (linear where the published models are multiplicative; ignores the bases involved and the off-target's own PAM; saturates at 0) and points to `CalculateMitSpecificityScore` / `CalculateCfdSpecificityScore`. Same declaration in the `crispr_specificity_score` tool description, `docs/mcp/tools/moltools/crispr_specificity_score.{md,mcp.json}`, the algorithm doc and the Evidence file. Two additive MCP tools expose the published aggregates: **`crispr_mit_specificity_score`**, **`crispr_cfd_specificity_score`** (with the `aggregation` enum). `FindOffTargets`' XML doc also now says `OffTargetScore` is the same heuristic, not a published per-hit model.
- **Tests:** `CalculateSpecificityScore_HeuristicAndMitAggregate_AreDistinct` (98.0 vs 50.0 on one input, so the two cannot be confused), and `tests/Seqeron/Seqeron.Mcp.MolTools.Tests/CrisprPublishedSpecificityScoreTests.cs` (12 cases incl. `SpecificityTools_HeuristicAndPublishedModels_AreDistinct`).

### F13 — CRISPR-OFF-001: three claims in the inherited WIP were not supported as stated (docs corrected, fixes kept)
- (a) **The non-ACGT off-target exclusion in the CFD genome overload is unreachable.** It was documented as reference parity ("Off-targets whose protospacer is not pure A/C/G/T are excluded from the sum, exactly as the reference does"). `DnaSequence` validates A/C/G/T at construction (`DnaSequence.cs` `ValidateSequence` → `SequenceExtensions.IndexOfInvalidDna`, `SequenceExtensions.cs:493-501`), so no ambiguous base can reach the scan. The guard is **kept** — it encodes the reference's `[^ATCG] → -1` rule (`crispor.py` **L2170-2185**) and stays correct if the genome type's alphabet ever widens — but is now documented as defensive and unreachable. Test `DnaSequence_RejectsAmbiguityCodes_SoNonAcgtOffTargetsCannotReachTheScan` pins the reachability argument.
- (b) **The claimed case-sensitivity disagreement was also unreachable** through the public API: `FindOffTargetsWithPamCore` upper-cases the guide and `DnaSequence` normalises the genome, so `CalculateOffTargetScore` could not have disagreed with the reported mismatch count. The dedup (penalty now iterating `GetMismatchPositions`, one case-folding rule for count/positions/penalty) is **kept** as the structural guarantee of INV-04; the claim is restated as defensive. Test `FindOffTargets_MixedCaseInput_CountPositionsAndPenaltyAgree`.
- (c) **The `EnsureMitModelApplies` doc quoted CRISPOR's Cpf1 banner selectively.** The quoted sentence continues "**We use Hsu and CFD scores below for off-target ranking**, but they were developed for spCas9" (`showPamWarning`, **L4724-4729**), which reads as the opposite of the refusal. The banner contradicts the code (**L1939-1942**, **L1986-1988** zero/sentinel both scores); the doc now attributes the quote, states that the code is taken as the reference behaviour, and the discrepancy is recorded in the Evidence file so it is not re-litigated.

### F14 — CRISPR-OFF-001: SaCas9 was scored with the `calcHitScore` fudge although the reference's own SaCas9 model is obtainable
- **Defect:** F9's fix scored SaCas9's 21-nt guides with `calcHitScore`'s last-20 fudge. But the reference does **not** do that: `annotateOfftargets` **L1943-1945** routes a SaCas9 PAM to `calcSaHitScore` (**L2025-2040**), the trained model of Tycko et al. 2018 (*Nat Commun* 9:2962). The previous review had recorded that model as "not obtainable as published parameters", which under campaign rule 2 would justify the fudge — **that is not the case**.
- **What was tried / what was found:** the GitHub contents API for `bin/src` returns **403** from this container and `bin/src/pairwise-library-screen/README` **404**s, so the directory cannot be listed — presumably why it was thought unobtainable. Using the exact paths named inside `predictSingle.py` instead, `raw.githubusercontent.com` serves both the scorer (`bin/src/pairwise-library-screen/predictSingle.py`, 2 567 B, **200**) and the trained coefficients (`models/rstan_mult_21_coeffs.txt`, 25 771 B, **200**; also `_20_` 25 053 B and `_22_` 27 119 B, both **200**). The tables are plain TSV, so `pandas` is not needed.
- **Cross-check:** `SaCas9Scorer` transcribed verbatim into Python with the TSV read in place of `pandas` (throwaway scratchpad script, not checked in) and run against the downloaded table. The 12 x 21 C# coefficient table was additionally diffed **mechanically** against `rstan_mult_21_coeffs.txt` (parse `Median`, apply the same `guide_len - Position + 1` remap, regex-extract the C# arrays, compare cell by cell): **252 values compared, 0 mismatching cells, max abs diff 0.0**. The reference script's **own asserted values** reproduce exactly: identical pair → `1.0`; `("GCAACCACAAACCCACGAGGG","ACAAACACATACCCACAAGGA")` → `0.041293256150042444`; `("GGGTGAGTGAGTGTGTGCGTG","GAGCGAGTGGGTGTGTGCGTG")` → `0.13441983202750601`; and the 20-nt table's assert `0.314432049304524`. `calcSaHitScore` = ×100 → `100.0`, `4.1293256150042446`, `13.4419832027506`. All three reproduce in C# to 1e-9.
- **Fix:** new public `CalculateSaCas9HitScore(string, string)` with the 21-nt `Median` column transcribed verbatim (252 values = 21 positions × 12 mismatch types), the reference's key convention (`d` = complement of the off-target base, `r` = guide base with T as U — CFD's convention written in the opposite order, so `CfdComplement` is reused), the reference's position remap (`guideLenDict[guide_len - Position + 1]`, i.e. arrays indexed from the 5' end), its 5'-most-position skip and its gap/bulge refusal. `CalculateMitSpecificityScore(string, DnaSequence, …)` now picks the per-hit model by system exactly as `annotateOfftargets` does (`IsSaCas9Pam` mirrors `pamIsSaCas9`, **L901-903**); `CalculateMitHitScoreFudged` remains the `else` branch. Only the 21-nt table is transcribed — 21 nt is the guide length of this library's only SaCas9 system and `FindOffTargets` rejects any other, so the remaining tables would be dead data; other lengths are refused, not approximated.
- **Tests:** `CalculateSaCas9HitScore_PerfectMatch_Returns100`, `…_ReferenceOracles_Match` (2 cases), `…_CoefficientOrientation_NotReversed` (`dT:rC` index 1 `54.6734106002513` vs index 20 `10.569373315278801` — a table transcribed without the remap swaps them), `…_MismatchAtFivePrimeMostPosition_Ignored`, `…_InvalidInputs_Throw`, `…_LowerCaseInput_TreatedAsUpperCase`; the three SaCas9 genome-level F9 tests now lock the Tycko values.

### F15 — CRISPR-OFF-001: four more claims in the inherited WIP corrected on independent re-verification
The whole CRISPR-OFF-001 diff was re-verified claim by claim against freshly downloaded primary
sources (every URL and every reproduced number is listed in `docs/Evidence/CRISPR-OFF-001-Evidence.md`).
The code's *numbers* all held — including a mechanical 252-cell diff of the SaCas9 coefficient table
against `rstan_mult_21_coeffs.txt` (**0 mismatching cells, max abs diff 0.0**) and all three of
`calcSaHitScore`'s reference oracles. Four **documentation** claims did not, and were corrected:
- (a) **`FindOffTargets`' XML doc claimed the 0-mismatch exclusion matched "the reference's own
  on-target skip in `annotateOfftargets`".** It does not: that skip (**L1920-1929**) is scoped to the
  caller-supplied on-target locus, or in "auto-ontarget" mode to the single first 0MM hit, so a second
  perfect match elsewhere in the genome IS scored there. The claim of parity is removed and the real
  deviation is now recorded in the XML doc, the algorithm doc and the Evidence file (divergence 10).
- (b) **The `crispr_mit_specificity_score` tool description said SaCas9's 21-nt guides "are scored on
  their last 20 nt, exactly as the reference `calcHitScore` does".** That contradicts the code it
  describes (and F14): SaCas9 is routed to the Tycko 2018 model, exactly as `annotateOfftargets`
  routes it. Rewritten to state the per-system routing.
- (c) **`crispr_cfd_specificity_score`'s doc said the reference emits "`cfdScore = -1` /
  `guideCfdScore = -1`" for SaCas9.** Only the per-hit sentinel is real; the reference's SaCas9
  guide-level value is a vacuous 100 (see divergence (g) above). Corrected in the tool doc, the tool
  description and the `CalculateCfdSpecificityScore` XML doc — the refusal is *better* than the
  reference here, and now says so for the right reason.
- (d) **`CalculateMitHitScoreFudged`'s XML doc implied its >20-nt and 19-nt branches are live.** With
  this library's system set they are both dead: the only PAM-after-target systems are SpCas9 (20),
  SpCas9-NAG (20) and SaCas9 (21), and SaCas9 goes to the Tycko model. Both branches are kept (the
  reference applies them) but are now documented as unreachable today.
Also corrected: eight `crispor.py` line citations in the Evidence file and in this report that were
off by a line or two (`L1915-1921`→`L1920-1929`, `L2047-2068`→`L2047-2067`, `L2025-2043`→`L2025-2040`,
`L2180-2182`→`L2181-2182`, `L1959-1961`→`L1960-1962`, `L1947-1957`→`L1947-1958`); the two
`scratchpad/ref/*.py` harness paths cited as if checked in (they are throwaway scripts — the Evidence
file now states what they contain so they can be rebuilt from the URLs); an unsupported
"suited to reference sequences up to roughly 1 Mb" envelope in the algorithm doc (no such measurement
exists — replaced with the structural statement that the scan is a naive PAM sweep, not CRISPOR's
BWA search); the `#L` source anchors in the two new MCP tool docs (stale after the edits); and the
